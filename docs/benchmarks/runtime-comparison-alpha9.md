# Docker Compose · K3s · Shearwater 같은 장비 비교 (alpha.9)

2026-11-17에 같은 장비에서 같은 nginx 앱으로 세 도구를 잰 기록이야. 측정한 Shearwater는 공개 alpha.9야. 이후 버전에서는 다시 재지 않았어. 2026-11-23에 로컬 측정 기록에서 이 문서로 옮겼어.

**이 표는 제품 순위가 아니야.** 세 도구는 기능 범위가 달라. K3s는 DNS, Ingress, 권한, 스토리지를 켠 기본 구성으로 쟀고, Shearwater는 단일 노드에 제한된 리소스만 지원해. 아래 수치는 이 앱, 이 장비, 이 설정에서의 관측이야.

[사례별 측정값 CSV](runtime-comparison-alpha9.csv) · [Shearwater가 하지 않는 것](../compatibility.md) · [도구별 용도 비교](../choosing-shearwater.md)

## 숫자를 읽는 방법

**앱 10개**는 같은 웹 앱을 독립된 앱으로 10개 띄웠다는 뜻이야. 한 서비스의 복제본 10개가 아니야. 앱은 요청마다 1,024바이트를 돌려줘.

**전체 프로세스 PSS**는 `sw` 프로세스 하나의 메모리가 아니야. 엔진, containerd, shim, 앱, 보조 프로세스를 모두 더한 값이고 공유 페이지는 나눠서 계산해. 측정 감시용 Python 프로세스(약 7MiB)도 세 도구 모두 들어 있어. 유휴 구간의 표본으로 구했어. Windows와 WSL 운영체제 전체는 들어 있지 않아. 다른 문서의 `sw server` RSS 약 30MB대는 `sw` 프로세스만 본 숫자라서 이 표와 비교하면 안 돼.

**cgroup 전체**는 Linux가 시험 묶음에 청구한 프로세스, 커널, 파일 캐시 메모리야. 캐시가 어느 실행에서 처음 읽혔는지에 따라 달라질 수 있어서 PSS와 같이 봐야 해. 기존 앱을 건드리지 않으려고 OS 파일 캐시를 강제로 비우지 않았어.

**배포 준비**는 이미지가 이미 받아진 상태에서 배포 명령을 시작한 시점부터 모든 앱이 준비 상태이고 HTTP 본문이 맞을 때까지야. 인터넷 속도, 처음 설치, WSL 부팅은 들어 있지 않아. 준비 검사 간격은 5초로 같지만 첫 검사 시점과 도구가 상태를 알려 주는 방식이 달라. Compose의 값이 길다고 해서 컨테이너 실행이 그 배수만큼 느리다는 뜻은 아니야.

**평상시 p95**는 초당 총 200요청을 30초 동안 보냈을 때 성공한 요청의 95% 지점이야. 요청마다 새 TCP 연결을 썼고, 요청 하나의 제한 시간은 2초, 부하 도구의 동시 요청 한도는 512개야. 앱이 10개일 때는 앱마다 초당 20요청을 보내 합계를 200으로 맞췄어. 최대 처리량 측정이 아니야. 1ms 안팎의 차이를 실제 사용자가 느낄 차이라고 보지 않아.

**업데이트 오류**는 45초 동안 요청을 계속 보내면서 10초 지점에 v1에서 v2로 바꾼 결과야. 3회 합계가 27,000건이야. 자동 재시도는 없고, 바뀌는 동안에는 v1과 v2 응답을 모두 정상으로 봤어. Kubernetes 쪽 두 도구는 `maxUnavailable=0`, `maxSurge=1`이고 Compose는 `up --wait`야. K3s 앱 1개의 오류 942건 중 819건은 2초 제한 시간을 넘긴 요청이야. 오류 0은 이 관측 범위의 0이야. 어떤 앱에서도 끊기지 않는다는 보장이 아니야.

**연결 경로**도 달라. Compose는 기본 포트 공개의 localhost 주소이고, K3s와 Shearwater는 커널이 전달하는 Service IP야. Compose의 `docker-proxy` CPU도 전체에 들어 있어.

## K3s의 업데이트 오류는 종료 설정에 따라 달라졌어

본 표의 K3s는 기본 제공 구성요소를 그대로 두고, 세 도구 공통 앱 설정(종료 유예 5초, 종료 전 훅 없음)으로 쟀어. Kubernetes 기본 종료 유예 30초를 그대로 시험한 것이 아니야.

같은 앱 1개로 종료 설정만 바꾼 대조 시험을 따로 했어. 기본, 대기, 대기, 기본 순서로 각 45초씩이야.

| 순서 | 설정 | 업데이트 오류/요청 |
| ---: | --- | ---: |
| 1 | 공통 설정 (유예 5초, 훅 없음) | 286/9,000 |
| 2 | 종료 전 5초 대기 + 유예 10초 | 0/9,000 |
| 3 | 종료 전 5초 대기 + 유예 10초 | 0/9,000 |
| 4 | 공통 설정 (유예 5초, 훅 없음) | 339/9,000 |

합계는 공통 설정 625/18,000, 종료 대기 설정 0/18,000이야. **K3s가 무중단 업데이트를 못 한다는 뜻이 아니야.** 종료 전 대기를 넣으면 이 앱에서 오류가 사라졌어. 앱 1개, 설정마다 2회의 대조야. 앱 10개 조건은 대조하지 않았고 커널 안의 정확한 원인도 확정하지 않았어. 5초 대기가 모든 앱에 충분하다는 뜻도 아니야.

Shearwater는 새 연결 대상에서 옛 Pod를 먼저 빼고 기존 연결을 기다리는 동작이 기본으로 들어 있어. 이 시험이 그 동작을 오류 0건의 원인으로 따로 분리해 확인한 것은 아니야. [연결 유지 원리](../connection-continuity.md) · [Kubernetes의 Pod 종료 흐름](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination)

Compose의 오류도 프로그램 결함으로 보지 않아. Compose의 기본 교체는 바뀐 컨테이너를 멈추고 다시 만들어. 프록시를 두고 두 벌의 앱을 운용하면 다른 결과를 만들 수 있지만, 그 구성의 비용은 이 시험에 넣지 않았어.

## 기능 차이

| 하고 싶은 일 | Docker Compose | K3s | Shearwater alpha.9 |
| --- | --- | --- | --- |
| 한 서버에서 앱 묶음 실행 | Compose 파일로 잘 맞음 | Kubernetes 객체와 클러스터 준비 필요 | 제한된 Kubernetes 객체와 `sw` 명령 |
| 일반 업데이트 | 변경 컨테이너를 멈추고 다시 생성 | Deployment 롤링 업데이트 | Deployment의 제한된 롤링 업데이트 |
| 이름으로 서비스 찾기 | Compose 네트워크의 서비스 이름 | 기본 CoreDNS | Service IP, Service DNS 없음 |
| 외부 HTTP 라우팅 | 포트 공개, 별도 프록시 | 기본 Traefik Ingress 등 | 이 시험 시점에는 별도 프록시 필요 |
| 영속 데이터 | volumes, bind mount | PVC, 기본 local-path | hostPath, emptyDir. PVC/CSI 없음 |
| 권한·격리 | Docker 보안 설정과 OS 권한 | RBAC, ServiceAccount, Pod 보안 | 로컬 관리자 토큰. securityContext는 저장만 |
| 여러 서버 | 일반 Compose 범위 밖 | 지원 | 단일 노드만 |

작은 앱 몇 개를 빨리 운영하려면 Compose가 자연스러운 기준이야. Kubernetes 생태계와 권한, DNS, 스토리지, 다중 노드가 필요하면 K3s의 추가 메모리가 그 기능의 비용이야. K3s는 기능을 끄면 더 작아질 수 있어서 이 값을 K3s의 최소 메모리로 읽으면 안 돼.

## 측정 환경

- CPU Ryzen 5 7500F(6코어 12스레드), Windows 물리 메모리 32GB.
- WSL 2 Ubuntu 24.04, Linux 6.6.87.2, WSL VM 메모리 약 3.82GiB. 운영 앱과 분리한 별도 WSL 배포판·cgroup·네트워크에서 쟀어. 다만 같은 PC에서 기존 앱과 다른 프로그램이 켜져 있었으니 전용 실험 장비의 결과는 아니야.
- K3s 실행에 필요해서 측정하는 동안 세 도구 모두 `vm.overcommit_memory=1`, `kernel.panic=10`으로 두었고 끝난 뒤 되돌렸어.
- Docker Engine 29.10.0, Compose 5.7.1, K3s v1.37.2+k3s1, `sw` alpha.9.
- Compose와 Shearwater는 같은 containerd v2.4.2 배포 파일을 썼어. K3s는 자체 번들 실행기야.
- 이미지는 nginx 1.28.0-alpine을 같은 digest로 고정했어. 원격 pull을 막고, 같은 앱으로 한 번 예열하고 정리한 뒤에 쟀어.
- 시험 묶음마다 CPU 4개, 메모리 2.5GiB 상한, swap 금지. 앱은 각 0.5 CPU, 64MiB. Go로 짠 실행기에는 모두 `GOMAXPROCS=4`를 줬고, 앱 접근 로그는 껐어.
- Docker 측정 대상은 WSL 안의 Linux Docker Engine과 Compose야. Windows의 Docker Desktop은 들어 있지 않아.
- K3s는 기본 DNS, Traefik Ingress, metrics-server, local-path-provisioner, ServiceLB를 켠 상태야. 처음 설치 작업은 본 측정에서 뺐어. 구성요소는 기본 그대로지만 실행 인자는 바꿨어. 격리를 위해 별도 주소·데이터 경로와 cgroupfs를 썼고, kube-proxy가 공유 커널의 conntrack 값을 바꾸지 않게 했어(`conntrack-max-per-core=0` 등). kubelet 축출 기준은 memory.available 100Mi, nodefs.available 5%야.
- 요청을 만드는 프로그램, 측정 수집기, 배포를 요청하는 CLI는 메모리와 CPU 집계 밖이야.

## 이 측정이 말하지 않는 것

- 최대 처리량, 24시간 안정성, 다중 노드, 긴 연결, 실제 운영 앱의 성능.
- 앱 수를 100개로 늘렸을 때의 메모리. 1개와 10개 두 점으로 직선을 긋지 않아.
- alpha.9 이후 버전의 수치. 이후 릴리스에서는 이 비교를 다시 하지 않았어.
- AI 운영 인터페이스의 정확도나 비용. 이 시험은 HTTP와 자원만 쟀어.

Shearwater 앱 10개 업데이트 구간에는 CPU 제한으로 기다린 누적 시간이 반복마다 1.009, 2.076, 1.003초 기록됐어. K3s는 같은 구간에서 중앙값 4.242초(2.593~5.177초)였어. 여러 컨테이너를 한꺼번에 만드는 순간에는 4코어 상한에 걸릴 수 있다는 뜻이야. 누적값이라서 서비스가 그만큼 끊겼다는 뜻은 아니야.

K3s 앱 1개 첫 반복에서는 새 버전이 준비됐다는 표시 뒤 마지막 5초에도 오류 44건이 있었어. 나머지 17사례는 마지막 5초가 모두 오류 없는 v2 응답이었어. 이 18사례 안에서 어느 도구에 불리한 결과도 빼지 않았어.

이 18사례 전에 조건을 보완하느라 통째로 버린 비교군이 있어. 이미지 digest를 고정하고 예열하기 전의 첫 시도, 부하 도구의 동시 한도가 64개여서 요청 일부를 보내지 못한 군, 메모리 부족으로 중단한 파일럿이야. 도구별로 골라서 뺀 것은 없어.

## 원본

[runtime-comparison-alpha9.csv](runtime-comparison-alpha9.csv)는 18사례의 집계값이야. 한 줄이 한 사례이고, `idle_`, `load_`, `update_`로 시작하는 열이 각각 유휴, 평상시 부하, 업데이트 구간이야. 위 표의 PSS와 cgroup 값은 `idle_pss_mib`, `idle_memory_mib`의 중앙값이고, CPU와 p95는 `load_cpu_one_core_percent`, `load_p95_ms`의 중앙값, 배포 준비는 `deploy_s`의 중앙값이야. 업데이트 오류는 `update_errors`의 3회 합계야. `trial` 값의 `cap512`는 부하 도구의 동시 한도가 512개인 비교군이라는 뜻이고, `_wsl_busy_`가 들어간 열은 다른 작업이 섞인 WSL 전체 CPU라서 특정 도구의 사용량으로 읽으면 안 돼.

요청별 기록과 1초 간격 자원 표본은 저장소에 넣지 않았어. 이 측정에 쓴 스크립트는 이 PC의 시험 전용 경로에 묶여 있어서 그대로는 다른 장비에서 재현되지 않았어. 같은 측정 규칙을 경로에 묶이지 않게 옮긴 스크립트와 GitHub Actions 워크플로가 이제 저장소에 있어. minikube도 비교군에 들어가. [CI 런타임 비교](runtime-bench-ci.md)를 봐. 장비와 메모리 상한이 달라서 그 결과를 이 표와 섞으면 안 돼.
