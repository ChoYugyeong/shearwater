# 작은 서비스에 어떤 운영 도구를 고를까

2026-11-17 공식 문서 확인 기준이야. **작은 서비스라는 이유만으로 Compose가 과도한 것은 아니야.**
Shearwater의 목표는 서버 한 대나 몇 대에서 컨테이너의 재시작·준비 확인·업데이트 기능을 쓰면서,
AI에게 맡긴 작업의 대상·승인·실행·접속 결과를 프로그램이 일관되게 관리하는 거야.
아직 실험적 알파이며 외부 사용자의 채택이나 시장 수요는 확인하지 못했어.

## 이미 좋은 대안이 있어

| 선택 | 공식 자료에서 확인한 강점 | Shearwater를 판단할 때의 의미 |
|---|---|---|
| Docker Compose | [단일 서버 운영](https://docs.docker.com/compose/how-tos/production/)을 안내해 | 익숙한 앱 정의와 운영 자동화가 있다면 계속 쓰는 선택이 합리적이야 |
| Docker Gordon | [환경을 읽고 변경을 제안·승인받아 실행](https://docs.docker.com/ai/gordon/)해 | AI 연결과 승인 기능 자체는 우리만의 차별점이 아니야 |
| Coolify | [MCP 연결](https://coolify.io/docs/mcp/overview)과 [작업별 기능 발견](https://coolify.io/docs/mcp/capabilities/overview)을 제공해 | 배포 관리 플랫폼과 AI 연결을 함께 원하는 사람의 대안이야 |
| Dokploy | [공식 MCP](https://docs.dokploy.com/docs/core/mcp)로 배포·로그·DB·도메인을 다루고 도구 preset과 비밀 필드 가리기를 제공해 | 도구 목록을 줄였다는 것만으로 경쟁 우위를 주장할 수 없어 |
| Kamal | [이미지 빌드·배포·HTTP 준비 확인](https://kamal-deploy.org/docs/commands/deploy/)과 [이전 이미지 복귀](https://kamal-deploy.org/docs/commands/rollback/)를 제공해 | 서버에 웹 앱을 배포하는 완성된 흐름이 중요한 사람의 대안이야 |
| Dokku | [한 서버의 오픈소스 PaaS](https://dokku.com/docs/getting-started/installation/)로 Git push에서 빌드와 실행을 이어가 | 코드에서 배포까지 자동화가 우선이라면 먼저 비교할 만해 |
| K3s | [단일 서버·고가용성 Kubernetes 구조](https://docs.k3s.io/architecture)를 제공해 | Kubernetes 생태계와 여러 노드가 필요하다면 지원 범위가 크게 달라 |

이 표는 기능 범위를 조사한 결과야. 이 제품들을 모두 같은 장비에서 실행해 속도를
비교했다는 뜻이 아니야. 문서에서 어떤 보장을 찾지 못했다고 그 기능이 없다고 판정하지 않아.
가격·최소 요구 메모리·별점으로 실제 사용 비용이나 보안을 대신 평가하지도 않아.

## Shearwater가 집중할 사용자

- Linux 서버 한 대나 몇 대에 신뢰하는 작은 HTTP 앱 몇 개를 올려 보는 개인 개발자.
- 이미 만든 이미지와 준비된 서버를 가지고, Qwen·Claude·Codex·DeepSeek 등으로 반복 운영을 맡기려는 사람.
- AI가 잘못된 앱 ID를 고르거나 지난 정상 상태를 새 배포 성공으로 착각하는 일을 줄이고 싶은 사람.
- 변경 원문을 확인하고 승인할 수 있으며, 알파의 지원 한계를 이해하고 실험할 수 있는 사람.

**가설은 “작은 관리 비용 + 한 번 선택한 앱의 검증 가능한 AI 운영”이야.**
이미지 참조와 앱 UID, 원래 변경 목표, 실행 기록을 모델의 기억 대신 프로그램이 보관해.
내장 대화는 실제 승인 대기에서 멈추고, 완료 판정에는 준비 상태와 내부 HTTP 검사를 함께 써.
이 흐름을 사용자가 따로 조립·관리할 필요를 줄이는 데 가치가 있다는 판단이야.
같은 설계를 Compose 위에도 구현할 수 있으므로 독점적인 기술이라고 주장하지 않아.

## 현재 더 필요한 것

`sw`는 단일 실행 파일이지만 containerd·runc·네트워크 도구는 별도로 필요해.
서버 설치, 인증 위임, 이미지 빌드, AI 클라이언트의 첫 등록, 공개 DNS/HTTPS는 별도 준비야.
AI가 이어가는 새 작업 흐름은 컨테이너 하나·내부 Service 하나의 HTTP 앱을 대상으로 해.
공개 주소·로그인·DB 마이그레이션 성공이나 데이터 복구까지 보증하지 않아.

서버의 여러 사용자 사이 권한 분리, 일반 Kubernetes 호환성, 여러 노드 운영을 제공하는
제품으로 고르면 안 돼. 앱 고정은 클라이언트의 실행 규칙이고 서버 RBAC가 아니야.
`securityContext` 등 저장만 하는 필드도 있어. [호환표](compatibility.md)를 먼저 확인해.
GUI에서 Git·도메인·DB를 한꺼번에 관리하고 싶다면 위 플랫폼들도 비교해 봐.

## 지금 가진 실험 근거와 그 한계

개발 과정에서 같은 nginx 앱으로 Qwen/DeepSeek와 Compose 시험용 MCP를 비교했어.
최종 후보는 Shearwater에서 두 모델 각각 3/3번 배포→업데이트→진단→승인 복구를 완료했어.
DeepSeek의 여섯 단계 전체 중앙값은 Compose 연결 196.6초/47,475토큰,
Shearwater 연결 177.3초/27,560토큰이었어. 모델 연결과 도구 실행을 포함한 값이야.

Compose 연결의 Qwen은 세 번 모두 업데이트와 HTTP 확인 뒤 호출을 끝내지 못했어.
엔진의 배포 실패가 아니며, 완료한 쌍이 없어 Qwen의 전체 시간 절감률은 계산하지 않았어.
이전 두 후보에서는 Compose/Qwen이 각각 2/3번 완료했어. 개선이 모든 도구 구성의 모델
행동을 좋아지게 했다고 해석하지 않아. 실패한 원본과 이전 결과도 보관했어.

각 군 3회, 한 앱, 한 장애 유형의 탐색 시험이야. Compose 예제는 1초 HTTP healthcheck,
Shearwater 기본 계획은 10초 TCP readiness를 사용했으며 최종 HTTP 검사는 공통이었어.
Qwen은 공통 시험 호스트, DeepSeek은 공식 CLI를 사용했으므로 모델 간 절대 비용도 비교하지 않아.
Compose 비교 도우미는 우리가 만든 시험 연결이며 Gordon·Coolify·Dokploy를 시험한 결과가 아니야.
인간 대신 사전에 정한 시험 조건을 확인하는 운영자 스크립트가 구체적인 계획을 승인했어.
이 숫자는 무인 승인, 일반 정확도, 시장 점유율, 항상 빠르다는 주장의 근거가 아니야.

기존 alpha.9 대비 새 후보의 기본 Go 실행 파일은 약 107KiB(0.30%) 커졌고,
유휴 API 프로세스의 메모리 관측 범위는 겹쳤어. 이번 개선으로 RAM 절감을 입증하지 못했어.
AI 작업 연결에서 불필요한 도구·대상 인자를 줄였고, 실익이 확인되지 않은 호환 기능 삭제는 하지 않았어.
