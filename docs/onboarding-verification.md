# 기존 앱 연결·설치·세 AI 실제 검증

2026-11-17, alpha.10 이후 개발 변경의 기록이야. **새 릴리스나 운영 서버 교체 기록은 아니야.**
사용법은 [설치부터 AI 연결까지](onboarding.md), 전체 운영 흐름은 [AI 앱 운영](agent-workflow.md)을 봐.

## 무엇이 달라졌나

| 이전에 막힌 지점 | 변경한 동작 |
| --- | --- |
| 기존 앱이 `app: 이름` 같은 라벨을 쓰면 HTTP 검증 거부 | 실제 selector와 Deployment→ReplicaSet→Pod 소유 UID를 확인 |
| 앱과 Service 이름이 달라 연결할 수 없음 | 유일하게 일치하는 Service 자동 탐색, 여러 개면 명시적으로 선택 |
| 포트가 하나이고 앱 포트와 같아야 함 | Service 포트를 선택하고 숫자·이름 targetPort를 실제 컨테이너 포트로 해석 |
| 연결은 성공한 뒤에야 지원하지 않는 경로를 발견 | 작업 파일을 만들기 전에 경로·소유 관계 확인 |
| 토큰 복사·소유자·권한 설정을 사람이 직접 해야 함 | `sw setup --user ... --apply`가 일반 사용자 인증 준비·실제 권한 확인 |
| Windows MCP에 배포판·사용자·경로를 매번 조합 | `workflow mcp-config --platform=windows`로 실행 인자 생성 |
| 모델이 준비 확인을 너무 빨리 포기 | verify가 제한된 시간 동안 읽기만 반복 |
| Qwen이 접속 확인을 복구로, 업데이트를 새 배포로 혼동 | 작업 의미와 현재 앱 존재 여부를 안내하고 잘못된 요청은 거절 후 다음 동작 설명 |

라벨 제한을 단순히 삭제한 것은 아니야. Service UID·IP·selector·선택 포트를 저장하고,
다른 앱의 Pod나 EndpointSlice를 자신의 성공 근거로 사용하지 않게 확인해.
연결한 뒤 경로가 바뀌면 새 연결을 요구해. 모델이 앱을 자동으로 바꿔 고르지 않아.

## 실제 모델 시험

운영과 분리한 QA WSL의 전용 네트워크·containerd·SQLite에서 실제 nginx 컨테이너를 실행했어.
같은 실행 파일과 두 개의 고정 이미지 digest를 사용하고 모델은 순서대로 실행했어.
Qwen은 로컬 Ollama, Claude는 로그인된 Claude Code, DeepSeek는 공식 명령줄 MCP를 사용했어.
모의 응답으로 모델 시험을 대신하지 않았어.

각 모델에 아래 일곱 작업을 요청했어. 각 단계의 실제 도구 결과와 별도 API·HTTP 조회로 판정했어.

1. 새 앱 배포 계획 저장.
2. 운영자가 정확히 승인한 계획 실행과 실제 HTTP 확인.
3. 기존 앱 형태로 다시 연결한 뒤 조회만 수행해 HTTP 확인.
4. 다른 이미지로 업데이트할 계획 저장.
5. 승인한 업데이트 실행과 HTTP 확인.
6. 실제 없는 이미지로 배포 실패를 만든 뒤, 원인 진단과 정상 이미지 복구 계획 저장.
7. 승인한 복구 실행과 HTTP 확인.

3번 준비에는 다른 이름의 Service, `app`·`tier` 두 라벨, 8080·8081 두 포트,
`targetPort: http` → 컨테이너 80, 환경 변수와 hostPath 저장 파일을 사용했어.
이 준비는 시험 운영자가 했고 AI의 성과로 세지 않았어. 8080 포트와 Service 이름은
명시적으로 선택했어. 변경 계획의 승인은 모델마다 3번, 모두 모델 밖에서 수행했어.

| 모델 | 완료한 작업 | 관찰된 도구 호출 / 오류 | 모델·도구 시간 합계 | 준비·승인 포함 사례 시간 |
| --- | ---: | ---: | ---: | ---: |
| Claude Code | 7/7 | 10 / 0 | 137.8초 | 151.9초 |
| Qwen | 7/7 | 12 / 1 | 61.0초 | 75.1초 |
| DeepSeek 공식 CLI | 7/7 | 10 / 0 | 246.9초 | 261.1초 |

**Qwen을 무오류라고 보고하지 않아.** 새 배포 단계에서 `verify`에 `image`를 잘못 붙인
요청 1회가 거절됐고, 모델이 올바른 배포 계획 호출로 수정해 완료했어. 기존 앱 조회 단계에서
변경을 시도하지 않았고, 최종 업데이트·복구도 실제 완료했어. 세 사례 모두 앱 UID가 유지됐고
업데이트·복구 뒤 환경 변수·볼륨 경로·저장 파일 SHA-256이 그대로였어.

한 모델당 최종 사례가 하나뿐이므로 일반적인 성공률이나 모델 간 성능 순위로 확대할 수 없어.
서로 다른 모델·로컬 GPU·클라우드·캐시·명령줄 시작 비용이 섞여 있고, 새 OS 준비 시간이나
이미지 다운로드 시간은 포함하지 않아. 이전 Compose 비교의 반복 측정군과 합산하지 않아.

### 토큰과 모델 식별

| 모델 | 입력 토큰 | 출력 토큰 | 캐시 읽기 | 캐시 쓰기 |
| --- | ---: | ---: | ---: | ---: |
| Claude CLI 보고값 | 32 | 5,521 | 27,995 | 13,316 |
| Ollama Qwen 보고값 | 17,940 | 566 | 별도 집계 없음 | 별도 집계 없음 |
| DeepSeek 단계별 보고 합계 | 9,516 | 12,502 | 25,472 | 0 |

Claude의 입력 32만 다른 모델의 입력과 비교하면 틀려. 캐시 입력이 별도 항목이기 때문이야.
출력에 사고 토큰이 포함되는 방식도 공급자마다 달라. 비용 절감률을 계산하지 않았어.
Claude CLI가 보고한 모델 ID는 `claude-opus-5-5`, Ollama 응답은 `qwen2.5:latest`였어.
DeepSeek 요청 설정은 `deepseek-v4-pro`/high였지만 응답이 정확한 모델 ID를 제공하지 않아
관찰 모델 ID는 미확인으로 남겼어. 명시한 MCP 목록과 실제 호출은 확인했지만 DeepSeek
내부 전체 도구 레지스트리를 독립적으로 출력해 검사한 것은 아니야.

## 처음 실패한 시험도 보관했어

- 첫 Claude 실행기는 Windows 프로세스 상수 오류로 모델 호출 전에 실패했어. 실행기를 고쳤어.
- 첫 기존 앱 전환 준비는 이전 Pod의 Ready를 새 전환 완료로 잘못 볼 수 있었어.
  시험 준비 조건을 고치고, 제품의 verify도 제한 시간 동안 준비를 기다리게 했어.
- Qwen의 접속 확인 요청에서 복구를 반복한 사례를 발견했어. 정상 진단 결과가 복구를
  유도하지 않게 바꾸고, HTTP 검증과 이미지 복구의 차이를 명확히 했어.
- Qwen이 기존 앱 업데이트에 deploy를 호출한 사례도 실패로 남겼어. 기존 앱 존재 여부와
  update 안내를 보완한 다음 새 사례로 처음부터 재시험했어.

실패한 기록을 통과 기록으로 덮어쓰지 않았어. 위 표는 마지막 공통 수정본의 세 사례만 세었어.

## 설치와 인증 확인

공개 alpha.10 압축을 실제 다운로드해 전체 압축과 내부 실행 파일 체크섬을 검사하고,
새 사용자 폴더에 설치한 파일의 버전을 확인했어. 기존 설치를 덮어쓰지 않았어.
이 설치기는 새 소스의 도구이며 공개 alpha.10 바이너리에 setup을 추가하는 기능은 아니야.

개발판으로 새 QA 서버 시작, 일반 사용자 인증 위임, 같은 setup 재실행 시 서버 유지,
기본 인증·작업 파일 경로 사용, Linux·Windows MCP 설정 출력을 확인했어.
이미 다른 서버의 인증이 있는 폴더는 거절했고 기존 파일 해시가 유지됐어.
생성한 Windows MCP 명령은 운영 앱의 조회·HTTP 검증으로도 실제 실행했어.

마지막 코드 검토에서는 **공개 건강 확인 URL의 성공을 인증 성공으로 착각할 수 있는 지점**을
고쳤어. `/readyz`뿐 아니라 인증이 필요한 `/api/v1/namespaces`까지 조회해야 통과해.
실제 틀린 토큰은 401로 거절됐고 새 인증 파일을 만들거나 서버를 재시작하지 않았어.
정상 토큰·일반 사용자·재실행도 다시 통과했어. 이 보강은 setup 전용이며 세 모델이 시험한
앱 운영·MCP 코드는 그대로야. 보강 뒤 Go 전체 테스트와 실제 인증 실패·성공 시험을 했어.

완전히 빈 OS에서 의존성까지 설치하는 시간은 측정하지 않았어. QA에는 이미 허용된
containerd·네트워크 도구가 있었어. WSL·런타임·이미지 빌드·AI 로그인 준비는 별도야.

## 기존 운영 앱과 회귀 검사

운영 sw 프로세스·앱 컨테이너 PID·재시작 수·UID·Pod IP를 유지했어.
앱 파일 32개, 설정 파일 8개, DB 객체 10개의 보존 비교와 SQLite 무결성 검사를 통과했어.
기존 Service 라벨을 바꾸지 않은 채 새 클라이언트의 내부 HTTP 검증이 성공했어.

Windows의 기존 앱 주소를 **3,869.9초 동안 19,307회** 요청했고 오류 0회, 본문 해시 변화 0회였어.
시험 QA의 종료·네트워크 정리도 이 관측 구간에 포함돼. Windows/WSL 재부팅을 이번에
다시 수행한 결과는 아니고, 관측하지 않은 시간의 무중단을 보장하는 수치도 아니야.

- `bash hack/t.sh`: Go 전체 테스트·vet·서식 검사 통과.
- Python 도구 검사: 66개 통과(설치기 경계 검사 3개 포함).
- Linux와 Windows kubectl을 포함한 M1: 103개, M0: 47개 통과.
- MCP: 20개, workflow: 19개, focused: 19개, chat resume: 6개 통과.
- 비공개 설명서 7편의 해시는 그대로이며 공개 소스에 추가하지 않았어.

## 코드를 읽는 순서

| 파일 | 읽을 내용 |
| --- | --- |
| `cmd/sw/setup.go` | root와 일반 사용자 경계, 토큰 전달, 덮어쓰기 거절, 실제 인증 확인 |
| `cmd/sw/workflow_route.go` | Service 탐색, 포트 해석, 소유 UID, 일관된 관측 |
| `cmd/sw/workflow.go` | 앱 연결, 계획·승인·한 번 실행, HTTP 검사와 기다림 |
| `cmd/sw/workflow_client.go` | 셸 문자열 대신 command/args로 MCP 설정 생성 |
| `cmd/sw/focus.go` | AI에 확인·신규 배포·업데이트·복구 의미를 전달 |
| `hack/install.py` | 제한된 다운로드, 두 체크섬, 새 폴더만 설치, 압축 경로 검사 |

재현할 때는 별도 서버에서 [시작 안내](onboarding.md)를 따라 같은 이미지·같은 앱 조건을
고정하고, 모델마다 새 작업 파일을 사용해. 모델의 최종 문장 대신 실제 MCP 결과와
별도 HTTP·데이터 해시를 확인해야 해. 실제 모델은 계정·버전·서버 상황에 따라 달라질 수 있어.
외부 사용자 체험, Compose/K3s 새 비교, 전체 보안 감사는 이번 결과에 포함하지 않아.
