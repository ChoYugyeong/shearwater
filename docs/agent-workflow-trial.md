# 처음 쓰는 사람을 위한 AI 운영 체험

이 안내는 alpha.10에서 도입한 [앱 작업 흐름](agent-workflow.md)을 작은 시험 앱으로 확인하는 순서야.
외부 참가자의 실제 결과는 아직 없어. 아래 양식과 기준은 결과를 받기 전에 정한 체험 설계야.

## 준비와 측정 구간

시험 담당자는 [설치 안내](install.md)대로 격리된 테스트 서버와 일반 사용자 인증을 준비해.
운영 앱과 다른 빈 앱 이름을 고르고 시험 앱만 변경할 수 있는 작업 파일을 제공해.
Docker/WSL/모델 설치와 계정 연결에 걸린 시간은 **환경 준비 시간**으로 따로 기록해.
준비된 상태에서 아래 일을 끝내는 시간은 **운영 작업 시간**이야. 두 값을 합쳤는지도 명시해.

`sw version`이 `0.1.0-alpha.14`인지 확인해. Qwen/Ollama 또는 MCP를 지원하는 클라이언트가
필요해. 비밀번호·토큰은 답변이나 기록 양식에 넣지 마. 서버 인증은 [위임 안내](agent-mcp.md)를 따라.
클라우드 모델을 쓰면 별도 계정과 사용 비용이 생길 수 있어.

## 1. 시험 앱에 한 번 연결하기

일반 사용자 터미널에서 실제 위임 경로와 API 주소를 넣어. `trial-web`이 이미 있다면
담당자가 새 이름과 새 폴더를 골라. 기존 파일이나 같은 이름의 앱을 덮어쓰는 실습이 아니야.

```bash
work="$HOME/.local/state/shearwater/trial-01"
install -d -m 700 "$work"
sw connect --workflow="$work/web.json" \
  --config-dir=/absolute/private/delegated-credentials --listen=127.0.0.1:6443 \
  --name=trial-web --image=nginx:1.27-alpine --port=80 \
  --http-path=/ --expect-body='Welcome to nginx!'
```

접속 확인이 실패하면 그 오류와 준비 시간을 기록하고 담당자에게 알려 줘.
이 명령의 출력에는 MCP 연결 설정이 있어. 사용하는 클라이언트의 프로젝트 설정에 연결해.
Qwen 내장 대화에서는 아래처럼 같은 파일을 사용해.

```bash
sw chat --workflow="$work/web.json" --allow-write --model=qwen2.5:latest
```

Windows Ollama를 쓴다면 [Windows 연결 예제](agent-workflow.md#qwen-내장-대화와-외부-deepseek)를 봐.

## 2. 배포 계획과 실행을 구분하기

AI에게 **“연결된 시험 앱을 배포할 계획을 만들어 줘. 적용 전에 멈춰.”**라고 말해.
실제로 저장된 계획이 나오면, 별도 일반 사용자 터미널에서 원문을 확인해.

```bash
sw workflow review --file="$work/web.json"
sw workflow approve --file="$work/web.json" --confirm=EXACT_PLAN_HASH
```

`EXACT_PLAN_HASH`는 방금 검토한 계획의 실제 값이야. 다른 앱이나 예상 밖 변경이 보이면
승인하지 말고 기록해. 승인 뒤 **“승인한 계획을 실행하고 준비 상태와 HTTP까지 확인해 줘.”**라고 말해.
앱 이름만 보여 주거나 모델이 성공했다고 말하는 것으로 끝내지 말고 실제 `healthy` 결과를 봐.

## 3. 빌드 결과 파일을 고르고 업데이트하기

일반 사용자 터미널에서 다음 시험 이미지 파일을 만들어 선택해.

```bash
printf '%s\n' '{"image":"nginx:1.28-alpine"}' > "$work/release-image.json"
sw workflow stage-image --file="$work/web.json" --image-file="$work/release-image.json"
```

이것은 이미지 선택이며 승인이나 배포가 아니야. AI에게 **“선택한 이미지로 업데이트 계획을
만들고 승인 전에 멈춰.”**라고 말해. 모델이 이미지 식별자를 다시 적을 필요는 없어.
2절처럼 원문 검토·승인 뒤 실행과 HTTP 확인을 맡겨.
여기의 태그 예시는 간단한 체험용이야. 반복 성능 비교에는 내용이 고정된 digest를 사용해야 해.

## 4. 새 배포 실패를 만들고 복구하기

시험 앱에서만 실패를 재현해. `.invalid`는 이 시험에서 일부러 사용할 수 없는 레지스트리 주소야.
담당자가 다음 파일을 선택하고, 참가자는 그 이미지 변경 계획을 정확히 검토·승인해.

```bash
printf '%s\n' '{"image":"invalid.invalid/shearwater-trial:missing"}' > "$work/broken-image.json"
sw workflow stage-image --file="$work/web.json" --image-file="$work/broken-image.json"
```

AI에게 **“선택한 시험용 이미지로 업데이트 계획을 만들어 줘.”**라고 말해.
2절과 같은 검토·승인 후 실행하면 새 이미지 준비가 실패해야 해. 기존 정상 컨테이너가
계속 응답할 수 있으므로 사이트 전체가 끊겨야만 성공한 장애 재현은 아니야.

이어 **“왜 새 배포가 안 되는지 실제 근거를 읽고, 마지막으로 접속까지 확인한 정상 이미지로
복구할 계획을 만들어 줘. 승인 전에 멈춰.”**라고 말해.
실제 오류 근거, 복구 대상 이미지, 다른 설정 보존을 확인하고 새 계획을 승인해.
실행 뒤 `healthy`와 HTTP 검사 범위를 다시 확인해. 이미지 복귀는 DB 변경을 되돌리는 기능이 아니야.
다음 업데이트를 할 때는 3절의 정상 이미지 파일을 다시 선택해.

## 5. 무엇을 기록하나

실제 업무의 순서는 연결 → 배포 → 업데이트 → 실패 재현 → 진단 → 승인 복구야.
승인은 정상 배포, 업데이트, 의도한 실패 이미지, 복구의 네 번을 각각 기록해.
예정된 승인은 도움 요청과 구분해. 시험 앱 정리는 담당자가 이번 작업의 앱/Service UID를 확인하고 맡아.

다음 양식을 복사해 채워. 모르는 값은 `미측정`으로 남기고 0으로 쓰지 마.

```text
참가자 임의 번호 / 평소 사용 도구:
날짜 / OS / sw 버전 / AI 클라이언트·모델:
환경 준비 시간 / 운영 작업 시간:
연결·배포·업데이트·실패 재현·진단·복구 각 완료 여부:
예정된 승인 횟수 / 계획 밖 도움 요청 횟수:
실제 실패한 단계와 오류(토큰·개인 경로는 제거):
예상 밖 대상 변경 또는 데이터 손실 여부:
관측한 토큰 사용량 / 단위 / 제공하지 않으면 미측정:
healthy와 실제 HTTP 확인 결과:
설명을 이해하기 어려웠던 문장:
지금 쓰는 도구 대신 다시 쓸 이유 / 쓰지 않을 이유:
7일 안에 스스로 다시 사용했는지(확인 전에는 미확인):
```

## 담당자의 비교 방법

처음 참가자 2~3명은 개발 경험·평소 Compose 사용 여부를 함께 기록해.
같은 앱·이미지·장비·모델·승인 정책을 제공하고, 두 도구를 비교한다면 순서를 번갈아 배정해.
실패나 중도 포기를 제외하지 말고 필요한 설명과 수동 수정도 모두 기록해.
설치 시간을 제외한 성공만으로 “처음부터 더 쉽다”고 결론내리지 마.

첫 제품 개선 판단 기준은 **3명 중 2명 이상이 계획 밖 도움 없이 완료**, **승인 없는 변경·
시험 외 앱 변경·데이터 손실 0건**, 그리고 구체적인 재사용 이유가 나오는지야.
이 숫자는 작은 체험을 위한 사전 기준이며 통계적 시장 검증이 아니야.
실제 참가자가 없는 현재 상태에서는 이 기준을 통과했다고 표시하지 않아.
