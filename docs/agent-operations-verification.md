# 서버 위임 작업의 실제 검증

2026-11-18, alpha.12에 포함한 기능의 **개발 중 검증 기록**이야. 아래 바이너리 해시와
측정값은 개발 후보에 해당해. 공개 소스 재빌드·운영 교체 검증은
[alpha.12 릴리스 기록](https://github.com/ChoYugyeong/shearwater/releases/tag/v0.1.0-alpha.12)에서 별도로 확인해. 사용법과 코드 읽는 순서는
[앱 하나의 운영을 AI에게 위임하기](agent-operations.md)를 봐.

## 무엇을 비교했나

같은 PC의 별도 WSL Ubuntu 24.04에서 같은 nginx 이미지 두 개를 사용했어.
실제 containerd 컨테이너, Service, HTTP 응답, 저장 파일을 확인했어.
모델의 “성공했습니다”라는 문장만으로 통과시키지 않았어.
장비는 Ryzen 5 7500F(6코어·12스레드), Windows가 보고한 물리 메모리 약 31.6GiB,
RTX 3050이야. 실행 중 관측한 Qwen 모델 digest는
`845dbda0ea48ed749caafd9e6037047aa19acfcfd82e704d7ca97d631a0b697e`였고,
Ollama는 모델 약 4.8GiB를 GPU에 올렸다고 보고했어. 다른 장비의 속도로 일반화하지 않아.

| 항목 | 기존 방식 | 새 방식 |
| --- | --- | --- |
| 클라이언트 | 공개 alpha.11 `sw connect` | 개발판 `sw task` |
| AI에 제공한 도구 | `sw_workflow` 하나 | `sw_workflow` 하나 |
| 권한 | 로컬 관리자 인증, 클라이언트의 대상 검사 | 한 앱·허용 동작·만료를 서버에서 제한 |
| 계획·실행 기록 | 클라이언트의 파일 | 서버 SQLite의 같은 트랜잭션 |
| HTTP 검증 | 준비 상태와 내부 Service | 새 배포의 각 Pod 직접 검사와 내부 Service |
| 복구 기준 | 클라이언트가 보관한 정상 이미지 | 실제 직접 검사까지 통과한 실행 digest |

이 비교는 **AI 운영 인터페이스의 비교**야. 두 방식의 컨테이너 실행 서버는 같은 개발판이고,
같은 준비 이미지와 동일한 앱 설정을 사용했어. Compose·K3s를 다시 측정한 시험이나
오케스트레이터 자체의 배포 속도 비교로 읽으면 안 돼.

### 반복 조건

각 모델·방식별 두 번, 한 번에 한 모델만 실행했어. 첫 반복은 기존 → 새 방식,
두 번째는 새 → 기존 방식이고 모델 실행 순서도 반대로 바꿨어.
각 단계는 새로운 모델 대화를 사용하지만 같은 연결 파일을 이어받아.

1. 새 앱을 실제로 조회하고 배포 계획 만들기.
2. 운영자가 정확한 계획을 승인한 뒤 적용·HTTP 확인.
3. 같은 앱을 다른 Service 이름·다중 포트·이름으로 된 targetPort에 다시 연결하고 조회.
4. 준비한 새 이미지의 업데이트 계획 만들기.
5. 승인 후 업데이트·HTTP 확인.
6. 의도적으로 없는 이미지를 배포한 뒤 실제 `ErrImageNeverPull` 진단·정상 이미지 복구 계획.
7. 새 승인 후 복구·HTTP 확인.

앱마다 정상 승인 세 번이 있어. 장애를 만드는 준비 단계의 승인은 별도 한 번이고,
이 준비를 AI가 수행한 성과로 세지 않았어. 승인 전에 실제 계획의 이미지·대상을 검사해.
잘못된 복구 이미지면 승인하지 않고 그 사례를 실패로 남겨.
적용 뒤에는 별도 검사기가 앱 UID, 원하는 이미지·준비 상태, HTTP, 환경 변수,
hostPath 설정, 저장한 파일의 SHA-256을 다시 확인해.

### 모델과 시간·토큰의 의미

- Claude Code의 실제 응답 메타데이터에는 `claude-sonnet-5-5`가 기록됐어.
- Qwen은 기존 Ollama의 `qwen2.5:latest`, 온도 0, 문맥 8,192, 출력 한도 2,048로 고정했어.
- 딥시크는 공식 CLI에서 `deepseek-v4-pro`, high를 요청했어. 제공자가 실행 응답에
  모델 ID를 반환하지 않은 경우 정확한 선택은 확인하지 못한 것으로 남겨.
  알려진 셸·파일·다른 MCP 도구를 호출별 설정에서 끄고 실제 추론 연결의 MCP 목록을 확인했어.
  CLI 내부의 모든 도구 등록 상태까지 완전하게 확인한 것은 아니야.
- 시간은 모델 대화 시작부터 끝까지이며 MCP·CLI 시작 시간이 포함돼. 이미지 준비,
  독립 검사, 사람이 계획을 검토하는 시간은 포함하지 않아. 전체 설치 소요 시간도 아니야.
- Claude는 입력·출력과 캐시 읽기·쓰기 토큰을 합치고, Qwen은 입력·출력 평가 수를,
  딥시크는 공식 단계별 `totalTokens`를 합쳤어. 모델마다 계산 규칙이 달라 **같은 모델의
  두 방식끼리만** 비교해. 합계 토큰을 API 요금으로 바꾸지 않았어.
- 완료하지 못한 사례의 짧은 시간을 “더 빠른 완료”로 세지 않아. 실패와 도구 오류도 남겨.
  모델이 틀린 계획을 내서 검증기가 막은 경우는 서버 보호 성공이면서 작업 완료 실패야.
- 승인 대기를 감지해 호스트가 중단한 경우를 모델이 스스로 잘 멈춘 것으로 세지 않아.
  추가 정답 안내나 수동 구조는 주지 않았고, 필수 승인 횟수와 구분했어.
  따라서 “추가 개입을 제공한 횟수 0”은 실패한 작업도 도움 없이 끝났다는 뜻이 아니야.
  GPU 모델 캐시를 매 단계 비우지는 않았으므로 시작 비용과 캐시 상태가 시간에 포함돼.

## 실제 결과

수정 전과 수정 후의 반복을 별도 기록으로 보존했어. 개발 중에 찾은 결함과 최종 후보의
결과를 섞어서 성공률을 만들지 않아. 원래 조건을 유지한 비교와 보완한 클라이언트 정책도
구분해. 각 단계의 시간·토큰·도구 오류는 [집계 원본](agent-operations-results.json)에 있어.

첫 개발판의 12사례는 기존 방식 4/6, 새 방식 3/6 완료였어. 새 방식의 Qwen 두 사례는 첫
배포 계획에서 멈췄고 딥시크 한 사례는 업데이트 계획을 만들지 않았어. 기존 Qwen 두 사례도
복구 계획 단계에서 완료하지 못했어. 이 결과를 개선 성과로 세지 않고 아래 수정을 진행했어.
두 번째 개발판의 12사례는 기존 방식 6/6, 새 방식 4/6 완료였어. Claude·딥시크는 양쪽 모두
배포부터 복구까지 두 번씩 통과했지만, 새 방식의 Qwen은 배포 후 기존 앱 검사에서 두 번
빈 응답을 보내 멈췄어. 새 방식 전체가 더 정확해졌다고 결론낼 수 없는 결과야.

두 번째 개발판에서 **완료한 사례의 중앙값**은 다음과 같아. 시간은 초야.

| 모델 | 기존 / 새 방식 완료 | 대화 시간: 기존 → 새 | 토큰: 기존 → 새 | 도구 오류: 기존 / 새 |
| --- | --- | --- | --- | --- |
| Claude | 2/2 / 2/2 | 103.7 → 129.3 | 44,887 → 46,766 | 0 / 0 |
| 딥시크 | 2/2 / 2/2 | 178.4 → 200.9 | 35,102.5 → 46,876 | 0 / 0 |
| Qwen | 2/2 / 0/2 | 80.8 → 완료 없음 | 14,851 → 완료 없음 | 2 / 4 |

오류 열은 각 방식의 두 번 전체에서 서버가 거부한 도구 호출 수야. 위 Claude·딥시크 결과는
`7e865234…` 개발판의 일곱 단계 시험이며, 이후 최종 후보의 반복으로 바꿔 표기하지 않았어.
첫 두 묶음 일부 구간에는 짧은 빌드·회귀 검사가 겹쳤으므로 엄밀한 속도 차이의 근거로
사용하지 않아. 추가 검증·새 배포·CLI 시작 비용이 포함된 운영 흐름의 관측치야.

### 최종 후보의 Qwen 반복

최종 후보 `9d3f7021…`와 공통 종료 규칙으로 다시 실행한 결과야. 이 네 사례가 끝나기
전에는 후보 실행 파일을 바꾸거나 다른 빌드·회귀 검사를 겹쳐 실행하지 않았어.

| 항목 | 기존 방식 | 새 방식 |
| --- | --- | --- |
| 배포부터 복구까지 일곱 단계 완료 | 0/2 | 2/2 |
| 완료 대화 시간 중앙값 | 완료 없음 | 85.9초 |
| 완료 토큰 중앙값 | 완료 없음 | 24,113 |
| 실패까지 포함한 두 사례의 시간 합계 | 136.5초 | 171.8초 |
| 실패까지 포함한 두 사례의 토큰 합계 | 22,331 | 48,226 |
| 두 사례 합계 도구 호출 | 19 | 29 |
| 두 사례 합계 도구 거부 | 2 | 6 |
| 실제 완료한 정상 변경 승인 | 각 사례 2회 후 중단 | 각 사례 3회 |

새 방식의 Qwen은 끝까지 완료했지만 **속도·토큰 절약을 입증한 결과는 아니야**. 기존 방식은
두 번 모두 장애 진단 뒤 `recover` 대신 `update`로 없는 이미지를 다시 계획했어. 승인 전
독립 검사에서 막혔고, 일곱 번째 단계를 실행하지 않았어. 단계 수가 다른 시간·토큰 합계로
속도나 비용 절약률을 계산하지 않아. 새 방식에도 서버가 거부한 호출과 모델의 수정 시도가
포함돼. 이 두 번으로 일반적인 성공률을 주장하지 않아.

직전 후보 `75171b18…`의 네 사례에서는 양쪽 모두 2/2 완료였고, 기존/새 방식의 완료 시간
중앙값은 79.1/83.6초, 토큰은 13,309/31,788이었어. 이후 실제 내장 대화에서 찾은 적용 기록
유실을 고쳐 최종 후보를 다시 시험했어. 양쪽에 같은 빈 응답 재요청·완료 종료 규칙을 유지했어.
직전 묶음의 더 좋은 기존 방식 결과도 공개 집계에 남겼어. 반복마다 결과가 달랐다는 사실도
두 번의 시험만으로 일반적인 우위를 판단할 수 없는 이유야.

첫 개발판 12 + 다음 개발판 12 + 고정 목록 후보 4 + 메모리 중단 전 3 + 종료 규칙 후보 4 +
적용 기록 보완 후보 4, 총 **39개 실행 사례**를 공개 집계에 포함했어. 별도로 메모리 부족으로 시작하지 못한
한 사례는 `unstartedCases`로 구분해. 시험 출력 경로 충돌로 시작 전에 멈춘 준비 시도는
모델 사례에 넣지 않았어.

## 반복 시험에서 발견해 고친 것

첫 개발판에서 Qwen은 이미 고정된 앱 이름·포트를 다시 보냈고, 거부 뒤에는 실제 도구 호출이
아닌 JSON 모양의 글을 출력했어. 딥시크는 현재 앱의 정상 검사를 준비한 새 이미지의 배포
계획으로 잘못 해석한 사례가 있었어. 통과한 사례로 바꾸거나 원본 기록을 지우지 않았어.

현재 구현은 다음을 보완했어.

1. `verifiedImage`와 `stagedImage`를 분리하고, 준비만 한 이미지가 있으면 현재 앱이
   정상이더라도 업데이트 계획이 남았다고 표시해.
2. 허용된 동작만 보여 주되 **연결 중에는 도구 목록을 유지해**. 일부 MCP 앱이 처음 받은
   목록을 계속 보관하므로, 현재 상태에 따라 `update` 등을 숨겼다 나타내는 중간 구현은
   제거했어. 현재 단계·이미지·승인은 요청마다 서버가 검사해.
3. `{"action":"verify"}` 같은 정확한 예시를 안내해. 내장 대화가 도구를 하나도 시도하지
   않은 채 빈 모델 응답을 받으면 한 번만 다시 응답을 요청해. 쓰기를 시도한 뒤에는 이
   방법으로 반복하지 않아. 실제 Qwen 비교에도 양쪽 방식에 동일한 재요청 정책을 적용하고
   추가 시간·토큰을 모두 포함했어.
4. 선택한 이미지 주소를 모델이 다시 보낸 경우 **서버가 고른 값과 정확히 같을 때만**
   받아들여. 다른 최초 배포·준비 업데이트·복구 이미지로 바꾸는 요청은 거부하고, 같은
   값을 반복해도 계획 검토·승인을 생략할 수 없어. 작은 모델이 선택적 `image` 필드를
   반복해서 넣는 실제 실패 때문에 추가한 처리야.
5. Qwen이 `healthy` 뒤에도 `continue`를 반복한 사례를 고쳤어. 내장 대화는 실제로 승인한
   적용의 HTTP 검증까지 끝나면 프로그램에서 턴을 끝내. 도구를 실행하기 전의 `verify`만
   정상인 경우에는 이 규칙을 사용하지 않아. 최종 Qwen 운전기에도 **양쪽에 같은 종료 규칙**을
   적용했어. 모델이 스스로 중단한 성과나 공개 alpha.11 내장 대화 그대로의 결과로 세지 않아.
6. 적용 기록을 저장한 뒤 HTTP를 검사하기 전에 다른 계획이 생기는 동시 변경도 다시
   확인해. 예전 계획에 나중 계획의 정상 검사 결과를 붙여서 반환하지 않아.
7. 실제 내장 Qwen 대화에서, 배포 적용 뒤 준비 상태를 기다리는 조회가 최종 응답의
   계획 번호·승인 정보를 덮어쓰는 문제를 찾았어. 기다리는 동안에는 읽기 검사만 하면서
   처음 적용한 계획의 기록을 보존하도록 고쳤어. 그 사이 앱 세대나 계획이 바뀌면 이전
   적용을 새 결과의 성공 근거로 붙이지 않아. 실제 TLS 요청으로 `continue` 한 번 뒤
   `verify`만 보내는지, 다른 계획이 끼어든 경우 성공 근거를 비우는지도 검사해.

모델의 글에서 JSON을 추출해 실행하거나, 거부된 다른 이미지를 임의로 무시하지 않았어.
빈 응답 처리도 외부 AI 앱 전체를 제어하는 기능은 아니야. 내장 `sw chat`과 이번 Qwen
시험 운전기에 적용했고, Claude·딥시크 CLI 자체의 재시도 정책을 바꾸지는 않았어.
고정 이미지 입력을 보완한 중간 묶음에서는 Qwen 기존 1사례·새 방식 2사례만 실행했어.
새 방식은 한 번 전 과정을 완료했고, 다른 한 번은 적용 자체가 정상이어도 반복 호출 한도에
걸려 완료 실패로 남겼어. 다음 기존 방식 사례는 Windows 여유 메모리 약 1GB로 시작 전
중단했어. 이 미실행 사례를 모델 실패나 성공으로 세지 않아.

## 자동 회귀 검사

수정본에서 다음 검사를 실제로 다시 실행했어.

| 검사 | 결과 |
| --- | --- |
| `bash hack/t.sh` — 포맷·정적 검사·전체 Go 테스트 | 통과 |
| Python 단위 검사 | 66개 통과 |
| MCP / workflow / focus / chat-resume | 20 / 19 / 19 / 6 통과 |
| M1 Linux + 실제 Windows kubectl | 103개 통과 |
| M0 Linux + 실제 Windows kubectl | 47개 통과 |

Go 검사는 제한 토큰의 원시 API 접근·자기 승인·타 앱 접근 거부, 만료·철회·토큰 교체,
동시 재시도, SQLite 재열기, 외부 설정 변경, 옛 Pod가 주는 200, 새 Pod의 잘못된 본문,
HTTP 검사 도중 컨테이너 교체·권한 철회, 현재 이미지와 준비한 이미지의 혼동을 다뤄.

Windows에서는 WSL의 Windows 실행 연결이 없어 `kubectl.exe` 직접 실행이 먼저 실패했어.
공유 커널 설정을 바꾸지 않고, 실제 Windows kubectl의 인자·출력·종료값을 작업 전용
파일 큐로 전달해 원래 M0/M1 검사문을 그대로 실행했어. 수정본용 큐를 복사할 때 생긴
줄바꿈 오류도 별도 실패 기록으로 보존한 뒤 LF 파일의 새 큐에서 103/47을 확인했어.
이 검증으로 WSL 실행 연결 자체를 고쳤다고 주장하지 않아.

추가 시험 준비 중에는 딥시크 운전기의 설정 파일 두 개를 복사하지 않아 추론 시작 전에
중단한 시도도 있었어. 누락 파일을 포함한 별도 기록 폴더에서 다시 연결했으며 이 실패를
모델의 판단 오류로 세지 않았어.

2초짜리 위임의 만료를 `sleep(2.1)`만으로 판단한 실제 시험은 한 번 실패했어. 당시 요청
시각과 서버 시각을 함께 기록하지 않아 정확한 원인은 확정하지 못했어. 별도의 실제 API에서
여덟 번 반복한 만료 검사는 모두 403 거부였어. 마지막 시험은 서버가 반환한 절대 만료
시각을 실제로 넘겼는지 확인한 뒤 요청하고, 대기 시간·요청 시각·서버 Date를 함께 남겨.
서버의 권한 검사 코드를 느슨하게 바꾸거나 실패 원본을 삭제하지 않았어.

마지막 실행 파일의 SHA-256은
`9d3f7021f427e7f6a24aa9b171c5a7d9616b36031220fb0f85c90f2c37c6487a`야.
아래 검사는 일곱 단계 비교와 별도로 수행한 기능 검증이야. 각 모델이 다른 역할을 맡았으므로
이때 걸린 시간을 모델 간 속도 비교에 사용하지 않아.

| 실제로 만든 상황 | 확인한 결과 |

제한 토큰으로 보낸 10가지 요청과 서버의 응답은 다음과 같아. 요청별 응답 코드는 공개 alpha.12 실행 파일(SHA-256 `8ac762baa28ff23e10e9b8207f724f1a929ba42998903a744cb7d9f7d63502db`)로 같은 시험을 다시 실행한 기록에서 옮겼어. 주 위임, 조회 전용 위임, 2초 뒤 만료되는 위임의 토큰 세 개를 썼어. 열 가지 모두 거부됐고 앱은 바뀌지 않았어.

| 제한 토큰으로 시도한 요청 | 응답 |
| --- | ---: |
| Kubernetes API 직접 읽기 | 401 |
| Kubernetes API 직접 쓰기 | 401 |
| 자기 계획을 스스로 승인 | 403 |
| 새 위임 만들기(범위 확대 시도) | 403 |
| 자기 토큰 만료 연장 | 403 |
| 요청에 다른 대상 앱 끼워 넣기 | 400 |
| 다른 작업의 식별자로 접근 | 403 |
| 조회 전용 위임으로 업데이트 | 403 |
| 철회된 위임 사용 | 403 |

위임 토큰은 Kubernetes API 경로에서 인증 자체가 되지 않아 401이야. 운영 API 안에서 권한 밖이면 403, 받지 않는 필드가 있으면 400이야. 같은 경계는 `internal/api/operation_test.go`와 `internal/operation/operation_test.go`의 단위 테스트로도 고정했어. Kubernetes 경로는 읽기 요청으로, 만료는 서버 내부 계층에서 확인해.

시험 앱의 UID, 환경 변수, hostPath 연결과 저장 파일 해시는 유지됐어. 앱 설정 세대는
승인한 변경에서만 증가했고, 응답 유실 뒤 이어받을 때는 다시 증가하지 않았어.
내장 Qwen의 읽기 전용 검증도 별도로 실행해 통과했어. 외부 Claude·딥시크는 실제 공식 CLI
연결이고, 이번 시험이 두 데스크톱 앱의 버튼·설정 화면을 직접 검사했다는 뜻은 아니야.

## 구현 비용과 기존 앱 보존

Go 1.27.3, `CGO_ENABLED=0`, `-trimpath` 조건의 실행 파일 크기는 공개 alpha.11의
36,646,972바이트에서 36,911,071바이트로 늘었어. 증가량은 264,099바이트, 약 **0.72%**야.
새 외부 라이브러리나 별도 상주 AI 서버는 추가하지 않았어. 기존 라이브러리와 SQLite를 사용해.

최종 시험 서버 한 시점에서 `sw`의 RSS는 31,028KiB였어. 내부 작업 기록 4개의 직렬화된
내용은 합계 10,318바이트, 가장 큰 기록은 6,005바이트였고, 시험 DB 파일 전체는
929,792바이트였어. 이 수치에는 SQLite 페이지·WAL과 컨테이너·containerd·모델 메모리를
같은 방식으로 합산하지 않았어. **새 기능의 메모리 증가량이나 전체 런타임 메모리 비교가
아니야.** 이번 변경의 CPU 증가량도 별도 측정하지 않았어.

기존 운영 서버는 공개 alpha.11 그대로 유지했어. 서버와 앱 PID, 재시작 수, 앱 파일 32개,
설정 파일 8개, DB 선언 객체 10개, 앱 UID·IP·컨테이너 상태를 전후 대조했고 DB 무결성도
정상이었어. 비공개 설명서 7편은 공개 소스 폴더로 옮기지 않아. 새 기능을 운영 서버에
배포하거나 Windows·운영 WSL을 재부팅한 시험으로 읽으면 안 돼.

Windows에서 기존 앱에 초당 한 번씩 보낸 두 관측 구간은 각각 3,598회/3,600.8초와
2,375회/2,376.8초였고, 합계 **5,973회에서 오류 0건**이었어. 같은 응답 본문 해시도
유지됐어. 두 구간의 마지막·첫 요청 사이에는 **361.7초의 미관측 공백**이 있으므로 약
100분 내내 연속 관측했다고 표현하지 않아. Windows 타이머 해상도로 지연 값이 0ms처럼
뭉친 기록이 있어 이 관측의 지연 백분위는 성능 지표로 사용하지 않아.

## 이 결과로 말할 수 없는 것

두 번씩의 작은 실험은 일반 성공률·성능 우위를 증명하지 않아. 외부 참가자는 아직 없고,
모델 제공자의 부하·캐시와 모델 업데이트도 결과에 영향을 줘. 태그 이름만 같은 모델이
앞으로 똑같이 행동한다는 보장도 없어.

실험 범위는 신뢰하는 한 서버의 단일 컨테이너 HTTP 앱이야. 공개 DNS·TLS·로그인·결제·
데이터 이전, 다중 노드, 서로 믿지 않는 사용자의 컨테이너 격리, 장시간 장애율은 측정하지 않았어.
AI가 별도 셸에서 관리자 인증을 읽을 수 있으면 그 권한까지 이 위임 토큰이 막아 주지는 않아.

차별화의 근거는 앱을 제한하고, 승인·실행·검증을 모델 밖에서 기록하고, 다른 모델이 같은
작업을 이어받을 수 있게 한 구조야. 모든 모델에서 더 빠르고 토큰도 적다는 주장은
실제 수치가 함께 뒷받침할 때만 할 수 있어.

## 다른 환경에서 재현하기

운영 앱이 없는 별도 Linux 환경에서 [위임 작업 안내](agent-operations.md)를 따라 새 앱을
만들고, 두 개의 고정 digest 이미지를 준비해. 실제로 성공한 현재 이미지와 새 이미지의
검사 문자열을 구분하고, 각 모델에 같은 요청을 보내. 각 단계의 실제 도구 호출·응답,
모델의 원래 사용량·벽시계 시간, 승인 계획, 별도 HTTP·파일 해시 검사를 남겨.

서버 중단 시험에서는 적용 응답을 일부러 받지 못한 뒤 **시험 서버만** 재시작해.
같은 연결 파일을 다른 모델에 넘기고 작업 상태를 읽어 검증하도록 해.
앱 UID·세대가 불필요하게 다시 증가하지 않았는지, 같은 저장 파일이 남았는지 확인해.
임의 문자열이 없는 HTTP 200도 실패로 잡는지 검사해. 실패 원본을 보존하고 변경한
소스·바이너리 해시를 분리하면 결과를 다시 해석할 수 있어.
