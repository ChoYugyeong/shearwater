# 연결 유지 개선 검증 기록

2026-11-14에 실행한 **개발 소스**의 검증이야. 공개 alpha.4 실행 파일은 이 변경을 포함하지 않아. 이번 작업은 공개 push·태그·릴리스나 운영 바이너리 교체를 수행하지 않았어. 동작 원리와 명령은 [연결 유지 안내](connection-continuity.md)에 있어.

## 측정 환경과 읽는 방법

| 항목 | 조건 |
|---|---|
| 호스트 | AMD Ryzen 5 7500F, 논리 CPU 12개, Windows에서 사용 가능한 메모리 약 31.6GiB |
| 실행 환경 | Ubuntu 24.04 WSL2, Linux `6.6.87.2-microsoft-standard-WSL2`, amd64 |
| QA 격리 | 별도 WSL 배포판, 전용 containerd 소켓, `shearwater` 네임스페이스, 사설 네트워크 네임스페이스 |
| 도구 | Go 1.27.3, kubectl Linux 1.36.6 / Windows 1.36.0, containerd 2.2.1, iptables-nft 1.8.10 |
| 앱 | 캐시된 nginx 1.27, Pod당 worker 1개, CPU 상한 500m·메모리 상한 64MiB |
| 롤링 전략 | `maxSurge: 1`, `maxUnavailable: 0`, HTTP readiness 검사, 원래 종료 유예 1초 |
| HTTP 부하 | 요청마다 1KiB 본문 비교, 연결당 32요청, 요청 제한 시간 2초, 자동 HTTP 재시도 0회 |
| 재시작 | TERM 또는 SIGKILL 뒤 의도적으로 sw 없이 5초 대기한 다음 시작 |
| SQLite·앱 파일 | Linux ext4의 새 QA 경로. 실행 후 증거 파일 보존 |

`maxUnavailable: 0`은 새 Pod가 준비되기 전에 기존 용량을 줄이지 않는다는 뜻이야. 이미 이전 Pod로 연결된 클라이언트를 보호하려면 별도의 연결 종료 대기가 필요해. 이번 시험에서는 두 기능을 함께 사용했어.

요청 성공 수와 오류 수를 먼저 보고, 다음에 지연시간을 봐. p95는 **성공한 요청 95%의 응답이 끝난 시간**이므로 오류를 숨기기 위한 지표로 사용할 수 없어. 로컬 네트워크에서 측정했으며 인터넷 왕복 시간은 포함하지 않아. 초당 1,000요청은 이번에 준 부하이고 최대 처리량이라는 뜻은 아니야.

## 자동 검사와 실제 통합 검사

| 검사 | 관측 결과 |
|---|---|
| `bash hack/t.sh` | gofmt 검사·go vet·Go 전체 테스트 통과 |
| M0 | Linux·Windows kubectl 합계 47 통과, 0 실패 |
| M1 | Linux·Windows kubectl 합계 103 통과, 0 실패 |
| M4 실제 runtime | 롤링 교체·scale·이력·되돌리기 검사 통과 |
| M5 실제 runtime | 순번 분산, 이름 포트, selector 변경, Pod 자기 Service 연결, 서버 중단 중 전달, Service/Pod IP 재사용 통과 |
| 1단계 통합 | 지원 범위의 시나리오 통과. SIGKILL 후 task 이어받기, 서버 중단 중 컨테이너 종료 따라잡기, 빈 실행 경로에서 네트워크 복구 포함 |
| root 격리 테스트 2개 | 기존 외부 주소·규칙 보존, 소유 표식 거부, 충돌 VIP의 DNAT 철회, 읽기 전용 검사 후 규칙 불변 통과 |
| 새 부하 스크립트 | Python 구문 검사, 변경한 셸 스크립트 구문 검사 통과 |

단위 테스트는 규칙 설치 전에 종료를 허용하지 않는지, conntrack 읽기 실패를 0개로 오인하지 않는지, 설치 중 새로 생긴 종료 대기를 이전 확인으로 처리하지 않는지 확인해. IP 정리에 실패하면 주소를 계속 예약하고 다음 성공 시도에서만 반납하는 경우도 검사했어.

1단계 스크립트의 `moby`·`moby_history` 직접 비교는 사용자 지정 금지 범위라 실행하지 않았어. 그 스크립트의 별도 footprint 단계는 이번 HTTP 부하 중 자원 측정과 구분해. Go race detector는 환경에 C 컴파일러가 없어 실행하지 못했어. 독립 에이전트의 최종 코드 검토를 받았다는 의미도 아니야.

## 실측 결과

**같은 최종 바이너리의 정상 HTTP 요청 112,000건, 오류 0건, 자동 재시도 0회**를 관측했어. 다음 표는 두 실행의 실제 통과한 HTTP 구간을 합친 것이야. 첫 실행 전체를 성공으로 바꿔 기록하지 않았어. 실행별 상태와 계산값은 [측정 JSON](testdata/connection-continuity-20261114.json)에 있어.

| 실행·구간 | 부하 조건 | 성공 / 오류 | 성공 요청 p95 | sw 관측 최대 RSS |
|---|---|---:|---:|---:|
| full3 · 정상 종료/재시작 | 15초, 80요청/초, 연결 8개 | 1,200 / 0 | 0.506ms | 29.42MiB |
| full3 · 부하 중 doctor | 10초, 80요청/초, 연결 8개 | 800 / 0 | 0.517ms | 28.01MiB |
| full3 · 강제 종료/재시작 | 15초, 80요청/초, 연결 8개 | 1,200 / 0 | 0.519ms | 28.00MiB |
| full3 · 확장/롤링/재시작 1 | 120초, 80요청/초, 연결 8개 | 9,600 / 0 | 0.506ms | 35.64MiB |
| full3 · 확장/롤링/재시작 2 | 같은 조건 반복 | 9,600 / 0 | 0.507ms | 37.07MiB |
| full3 · 확장/롤링/재시작 3 | 같은 조건 반복 | 9,600 / 0 | 0.493ms | 36.98MiB |
| full3 · 고부하 중 롤링 | 60초, 1,000요청/초, 연결 32개 | 60,000 / 0 | 0.293ms | 36.35MiB |
| full4 · 정상 종료/재시작 재검증 | 15초, 80요청/초, 연결 8개 | 1,200 / 0 | 0.457ms | 29.99MiB |
| full4 · 부하 중 doctor 재검증 | 10초, 80요청/초, 연결 8개 | 800 / 0 | 0.471ms | 28.18MiB |
| full4 · TERM/KILL 5회 반복 | 180초, 100요청/초, 연결 8개 | 18,000 / 0 | 0.426ms | 35.36MiB |

120초 구간에서는 10초에 3→10개 Pod로 확장하고, 40초에 롤링 교체, 80초에 서버 재시작을 수행했어. 고부하 구간의 실제 처리율은 약 999.72요청/초였어. 시작·종료 오버헤드를 포함해 계산한 값이야.

sw 자체의 관측 최대 RSS는 **37.07MiB**였고, 고부하 롤링 구간의 sw CPU 평균은 **한 코어 기준 약 7.22%**였어. RSS는 1초마다 읽은 값이라 순간 최대치를 보장하지 않아. CPU는 같은 PID와 시작 시각의 샘플끼리 사용 시간 차이를 계산했어. 서버가 없는 시간은 계산 가능한 실행 구간에서 제외했어. 커널·containerd·shim·앱·iptables 자식 프로세스·부하 발생기의 자원은 이 sw 수치에 포함하지 않았으므로, 전체 시스템 비용으로 해석하면 안 돼.

정상 HTTP 요청 집계와 별도로 다음 경계를 확인했어.

- 대상 목록을 0개로 바꾼 뒤에도 **같은 TCP 연결에서 100회 요청**이 성공했고 새 연결은 거부됐어. full3·full4에서 각각 실행했어.
- 1MiB 파일을 초당 64KiB로 천천히 받는 도중 롤링과 3초 서버 중단을 겹쳤어. 본문과 SHA-256이 일치했으며 full3·full4 모두 잘림 없이 완료했어. full4의 관측 시간은 15.12초였어.
- 계속 유지한 연결은 종료 대기 시작 관측으로부터 **30.24초** 뒤 예상대로 닫혔어. 322회 요청 뒤의 예상 종료이며 정상 요청 실패와 합치지 않았어. `ConnectionDrainTimeout` 경고도 실시간 watch로 기록했어.
- Service IP를 새 UID의 Service에 재사용했을 때 옛 연결이 거부됐어. 새 Service의 selector 복구 후에는 정상 부하를 다시 처리했어.
- sw 재시작 전후에 Pod UID·IP·컨테이너 ID·재시작 수가 같았어.

full3는 정상 HTTP 92,000건과 느린 다운로드를 통과했지만, **Pod 삭제 후 이벤트 목록을 조회하는 시험 방식** 때문에 마지막 assertion이 실패했어. Pod 소유 이벤트는 Pod와 함께 정리되는 기존 동작이야. 제품 바이너리를 바꾸지 않고 시험을 실시간 watch로 수정한 뒤 `full4 --extended-only`에서 해당 경계·IP 재사용·반복 재시작까지 통과했어. full3의 `passed: false`와 실패 원본은 보존했고, full4는 `passed: true`, 두 실행 모두 `cleanup: true`야.

실행 파일 SHA-256은 `4f3944c72aa41b10ddfff2154e95059f36fad7347c595b37a47adc7ea02c0db9`이고 크기는 36,243,092바이트야. 릴리스 패키지의 해시가 아니라 이 측정에 사용한 개발 바이너리의 식별자야.

## 기존 앱과 정리 확인

운영 alpha.4의 서버·앱 프로세스, 바이너리 해시, Pod UID·IP·Service IP·재시작 수를 유지했어. 설정 파일 8개, 앱 파일 32개, 저장 객체 10개와 IP 예약 2개를 비교했고 SQLite 무결성 검사도 통과했어. Pod 직접 주소, Service 주소, Windows의 기존 전달 주소에서 HTTP 200과 동일한 본문 해시를 확인했어.

QA의 sw·containerd 프로세스, 소켓, 사설 네트워크 네임스페이스, 외부 연결 veth와 전용 외부 체인이 남지 않았음을 마지막 읽기 전용 검사로 확인했어. DB·로그·측정 JSON·실패 증거는 보존했어. 원본 저장소와 이전 작업트리도 변경하지 않았어.

## 검증 중 발견해 보완한 경계

- 읽기 전용 시작·진단 검사가 전달 규칙을 지워서는 안 돼. 초기 후보에서 발견한 잘못된 정리 위치를 고치고, 실제 규칙이 그대로 남는 root 검사를 추가했어.
- 준비된 대상이 0개여도 마지막 DNAT 표현식이 사라지지 않게 했어. 기존 연결은 유지하고 새로운 연결은 거부하는 별도 검사가 있어.
- 주소가 같다는 이유만으로 연결 대상을 믿지 않아. Service UID, Pod UID와 IP 예약을 함께 검사하고, 주소 반납 전에 옛 연결 기록을 정리해.
- 규칙을 읽고 고르는 동안 DB가 바뀔 수 있어. 하나의 SQLite 읽기 트랜잭션으로 규칙과 종료 대기의 확인 대상을 같은 시점에 맞췄어.
- 커널 부하 분산도 기존 순번 분산 계약을 지켜. 실제 M5 검사에서 이 계약을 확인했으며 검사 조건을 완화하지 않았어.
- Pod가 자기 Service를 통해 자신에게 연결할 때 필요한 브리지 hairpin 설정을 소유 veth에만 추가했어.
- Service를 삭제할 때 전달 규칙 철회·연결 기록 정리를 마친 다음 VIP를 떼도록 순서를 정했어.

QA 자체의 격리 문제도 구분했어. QA에서 지운 VIP로 보낸 요청이 기본 경로를 따라 같은 IP를 쓰는 운영 앱에 도달했어. QA 규칙에서는 그 VIP가 사라졌고 응답 해시는 운영 앱과 같았어. QA 내부에서 외부로 나가려는 클러스터 대역을 차단한 뒤 같은 M5 검사를 통과했어. 운영 앱의 규칙을 바꾸거나 검사 조건을 느슨하게 만든 것이 아니야.

처음 QA 격리 규칙을 filter 테이블에 미리 넣었을 때, 이 환경의 iptables에서 없는 `DOCKER-USER` 조회가 `Incompatible with this kernel`로 실패했어. 격리 규칙은 QA의 mangle POSTROUTING으로 옮겨 제품이 검사하는 filter 테이블을 미리 구성하지 않았어. 제품에서 이 오류를 정상으로 취급하도록 바꾸지 않았으며, 다른 호스트에서도 같은 현상이 재현되는지까지는 확인하지 않았어.

M1의 이전 실행 중 Windows 실행 파일이 WSL에서 셸 파일로 해석되어 Windows 검사 12개가 실패한 기록도 보존했어. 최종 실행은 Windows kubectl 실행 가능 여부를 먼저 확인하고 동일한 검사 스크립트로 103개 모두 통과했어. 원인을 API 동작으로 잘못 분류하거나 실패 기록을 삭제하지 않았어.

## 재현·판정·남은 한계

[연결 유지 안내의 재현 절차](connection-continuity.md#실제-시험-재현)에 따라 빈 QA runtime에서 `hack/connection-check.py`를 실행해. 이전 시험의 DB나 디렉터리를 지우지 말고 새 `--root`, `--run`, `--out`을 사용해. API 회귀는 일반 사용자로, 실제 runtime 검사는 격리 네트워크 안에서 root로 실행해.

기본 시험은 10분 40초의 고정 부하에 배포·상태 확인·긴 연결 경계 시험 시간을 더한 길이야. 결과의 `phases`는 정상 HTTP 부하, `actions`는 재시작·느린 다운로드·예상 종료 같은 경계 조건이야. `binarySHA256`으로 실제 실행 파일을 식별해. 개발 버전 문자열만 같다고 다른 빌드 결과를 섞으면 안 돼.

이 결과는 24시간 안정성, 최대 수용량, 실제 외부 사용자 평가나 모든 앱의 무중단을 뜻하지 않아. 무한 WebSocket과 30초보다 긴 연결은 종료 대기 한도 뒤 닫힐 수 있어. Pod 직접 IP, 강제 삭제, 컨테이너 충돌, 노드·WSL 재부팅은 기존 TCP 유지 보장 대상이 아니야. alpha.4 프로세스가 이미 소유한 소켓은 최초 업그레이드 때 커널로 이전할 수 없어.
