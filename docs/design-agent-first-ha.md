# 설계: 에이전트 우선 강화와 컨트롤 플레인 고가용성(HA)

2026-11-25 시작. 기준은 공개 alpha.16(`f4289b2`). 작업 브랜치는 `agent-first-ha`
(worktree `G:\Dev\shearwater\worktrees\agent-ha`), push 안 함.

사용자가 한 말 세 가지가 출발점이야.

- "컨트롤 플레인도 여러 대여야 하지 않느냐."
- "AI 에이전트용이라는 장점이 잘 드러나지 않는다."
- "상태 저장소로 벡터 DB가 낫지 않느냐."

이 문서는 Claude·Codex·Gemini가 동시에 일하기 위한 **계약**이기도 해. 설계가 바뀌면 이 문서를
먼저 고치고 다른 작업자에게 알린다.

## 0. 먼저 답

**"왜 서버 한 대여야 해?"** 워커는 이미 여러 대 붙일 수 있어(alpha.16 `sw join`). 한 대뿐인 건
**컨트롤 플레인**이야. 상태 저장소인 SQLite는 쓰는 주체가 하나라서, 그 서버가 죽으면 API와 재배치가
멈춰(워커의 앱은 계속 돌아). 여러 대로 만들려면 상태를 다른 서버로 **복제**하고, 누가 쓰는지 **리더를
뽑는** 장치가 필요해. 이번 작업에서 그걸 설계하고 구현해(3절).

**"상태 저장소는 벡터 DB가 낫지 않아?"** 아니야. 상태 저장소(Kubernetes의 etcd 자리)는 "이 객체의
지금 값", "리비전 N 이후 바뀐 것"을 정확히 돌려줘야 하고, 트랜잭션·리비전·watch가 필요해. 벡터 DB는
"이 문장과 뜻이 비슷한 것"을 찾는 임베딩 유사도 검색용이라 역할이 달라. 다만 에이전트의 **보조 기억**
(과거 장애와 그때 한 조치를 뜻으로 찾기)에는 벡터 색인이 쓸모 있어. 그래서 SQLite는 원본으로 그대로
두고, 그 기능은 선택 기능 후보로 둬(2.4절).

## 1. 원칙

- 핵심 원칙 그대로: **경량화와 사용자 편의성**. 바이너리 하나, 노드마다 상주 프로세스 `sw` 하나.
- **새 외부 의존성 금지**(`go.mod` 변경은 사용자에게 먼저 묻는다). `k8s.io/*` 금지. 복제·선출·
  감사·임대 모두 직접 짠다.
- **되돌리기 호환**: alpha.16 실행 파일이 새 DB를 열 수 있어야 해(운영 교체 절차가 되돌리기에
  기대고 있어). 그래서 `schema_version`을 올리지 않고, 새 상태는 **새 표**(`CREATE TABLE IF NOT
  EXISTS`)로만 더한다. 옛 실행 파일은 새 표를 무시한다.
- 재지 않은 수치는 문서에 쓰지 않는다. HA는 "보장하는 것/안 하는 것"을 분명히 적는다.

## 2. 에이전트 우선 강화

### 2.1 지금 있는 것

| 기능 | 무엇을 해 주나 |
| --- | --- |
| `sw task` 위임 | 앱 하나·허용 동작·만료를 정한 제한 토큰, 계획 해시 승인, 정확히 한 번 실행, 새 Pod마다 HTTP 검증, evidence·diagnose·why |
| `sw mcp` | 집중 도구(`sw_target_*`), 워크플로 도구(`sw_workflow`), 진단 도구(`sw_get`·`sw_observe`·`sw_why`…), 계획/적용 |
| `skills/shearwater-ops` | 에이전트용 운영 안내(계획≠승인, 한 번만 적용, 원래 목표로 검증) |
| 오류 형식 | `CODE retry=safe|unsafe|never` + hint, dry-run |
| Compose 백엔드 | `sw compose serve`로 같은 위임·승인·증거를 Compose 앞에 |
| alpha.16 접근 제어 | RBAC, `sw user add`(네임스페이스 제한 kubeconfig), 쿼터, Pod Security |

### 2.2 빈 곳

코드와 문서를 대조해서 찾은 것이야.

1. **에이전트라는 개념이 없어.** 에이전트 하나를 붙이려면 운영자가 `sw user add`(또는 `sw task
   create`) → MCP 설정 손으로 쓰기 → 스킬 복사를 따로 해야 해. Claude Code·Codex·Gemini CLI마다
   설정 형식도 달라. "AI 에이전트용"이라는 말이 첫 경험에서 안 보이는 가장 큰 이유야.
2. **누가 바꿨는지 남지 않아.** `audit` 표는 스키마에만 있고 아무도 쓰지 않아(`internal/store/store.go`).
   `changes` 표에는 무엇이 바뀌었는지만 있고 누가 바꿨는지는 없어. 에이전트가 여럿이면 치명적이야.
3. **"내가 마지막으로 본 뒤 바뀐 것"을 싸게 물을 방법이 없어.** 에이전트는 매번 전체 목록을
   다시 읽어. 리비전 기반 변경 기록은 이미 있는데 에이전트용 요약 출구가 없어.
4. **여러 에이전트가 같은 앱을 동시에 만질 때 서로 모른다.** 같은 앱의 대기 중 계획은 거절되지만,
   "지금 누가 무엇을 하려고 이 앱을 잡고 있는지"(의도·만료)를 볼 수 없어.
5. **검증이 실패하면 사람이 올 때까지 깨진 상태로 남아.** `recover`는 있지만 새 승인이 필요해.

| 순위 | 기능 | 근거 | 담당 |
| --- | --- | --- | --- |
| 1 | **에이전트 신원 한 번에**: `sw agent add NAME --namespace NS --client claude|codex|gemini|all` | 빈 곳 1. 첫 경험을 바꾸는 입구. 기존 사용자·RBAC API를 묶기만 해서 위험이 낮아. 이름이 감사 기록(2)으로 이어져 | Gemini |

| 3 | **앱 임대(Lease)와 의도**: `coordination.k8s.io/v1` Lease, 위임 작업이 계획할 때 앱 임대를 잡고 다른 작업은 `APP_LEASED retry=safe`로 거절 | 빈 곳 4. kubectl 호환 자원이라 사람도 `kubectl get leases`로 봐 | Codex |
| 4 | **검증 실패 시 자동 되돌리기**: `sw task create --auto-recover` | 빈 곳 5. 위임할 때 운영자가 미리 허락한 범위("마지막으로 검증된 이미지로만")에서만 | Codex |
| 5 | **README를 에이전트 중심으로** | 사용자의 두 번째 지적. 1~4가 들어간 뒤에 써야 사실만 적을 수 있어 | Claude(초안 검토 Gemini) |

#### 2.3.1 `sw agent` (Gemini)

```
sw agent add NAME --namespace NS [--role edit|view|admin] [--client claude|codex|gemini|qwen|all]
             [--out DIR] [--server URL] [--config-dir DIR] [--listen ADDR]
sw agent list
sw agent remove NAME
```

- 내부적으로 `sw user add`와 같은 관리자 API로 사용자 자격 증명·네임스페이스·RoleBinding을 만든다.
  에이전트임을 구분하도록 RoleBinding과 네임스페이스에 라벨 `shearwater.io/agent=NAME`을 단다.
- `DIR`(기본 `./NAME-agent`, 권한 0700)에 쓴다:
  - `kubeconfig`(그 네임스페이스만, 기본 네임스페이스 = NS)
  - `sw mcp`가 읽을 연결 폴더(에이전트 토큰, CA, 주소) — 관리자 토큰은 절대 들어가지 않는다
  - `mcp/claude.json`(Claude Code `.mcp.json` 형식), `mcp/codex.toml`(`[mcp_servers.shearwater]`),
    `mcp/gemini.json`(Gemini CLI `settings.json`의 `mcpServers`), `mcp/qwen.json`
  - `skills/shearwater-ops/`(바이너리에 내장한 스킬 사본)
  - `AGENT.md`: 이 에이전트의 이름·네임스페이스·할 수 있는 일·승인 절차를 한 쪽으로
- 출력 마지막 줄은 각 클라이언트에 붙이는 한 줄 명령(예: `claude mcp add ...`)이야.
- `remove`는 토큰 폐기 + 라벨 붙은 바인딩 삭제. 네임스페이스와 그 안의 앱은 남긴다(`sw user remove`와 같음).

#### 2.3.2 행위자 기록과 변경 요약 (Claude)

- 새 표 `change_actors(rev INTEGER PRIMARY KEY, actor TEXT NOT NULL, via TEXT NOT NULL)`. 같은 쓰기
  트랜잭션 안에서 `changes`와 함께 쓴다. `changes`를 정리(compact)할 때 함께 지운다. 옛 실행 파일은 이
  표를 모르니 기록이 빠질 뿐 깨지지 않는다.
- 행위자: API 요청은 인증된 신원(`admin`, 사용자 이름, `system:node:NAME`), 서버 내부 컨트롤러는
  `system:controller:이름`, 위임 작업은 `task:ID`. `via`는 `kubectl`/`api`/`task`/`controller`/`node`.
- `sw changes [--since REV] [-n NS] [--actor NAME] [--limit N] [--json]`, 관리자 API
  `/shearwater/admin/v1/changes`, 일반 사용자는 RBAC로 볼 수 있는 네임스페이스만. 출력은 한 줄에
  `REV 시각 행위자 종류 이름 바뀐 필드(spec.replicas 2→3, image a→b)`. status 심장 박동 같은 소음은
  접어서 센다.
- MCP `sw_changes(since)`: 최대 50개, 넘으면 `next` 리비전과 "더 있음" 한 줄. 에이전트는 마지막으로
  받은 `next`만 기억하면 돼.

#### 2.3.3 앱 임대 (Codex)

- 자원 `coordination.k8s.io/v1` Lease(네임스페이스 자원): `spec.holderIdentity`,
  `leaseDurationSeconds`, `acquireTime`, `renewTime`, `leaseTransitions`. 표 열 `NAME HOLDER AGE`.
- 앱 임대 이름은 `shearwater-app-<앱>`, 의도는 주석 `shearwater.io/intent`.
- 위임 작업이 계획을 만들 때 그 앱의 임대를 잡고(보유자 `task:ID`), 적용·검증이 끝나거나 계획이
  버려지거나 만료되면 놓는다. 다른 보유자가 만료 전 임대를 갖고 있으면 `APP_LEASED retry=safe`
  + hint(보유자, 만료 시각, 의도).
- CLI `sw lease list|acquire|release`, MCP는 워크플로 상태에 "누가 잡고 있나"를 싣는다.
- kubectl로 직접 쓰는 사람은 막지 않는다(임대는 협조용). `sw changes`와 `kubectl get leases`로 보인다.

#### 2.3.4 자동 되돌리기 (Codex)

- `sw task create ... --allow update,recover --auto-recover`. `recover`가 허용돼 있어야 한다.
- 승인된 업데이트가 적용 뒤 HTTP 검증에서 확정 실패(`http_failed` 등)로 끝나면, 서버가 **마지막으로
  검증을 통과한 이미지**로 되돌리는 계획을 만들어 새 승인 없이 적용하고 다시 검증한다. 되돌릴 이미지가
  없으면 하지 않는다. 한 번 실패에 한 번만(되돌리기가 또 실패하면 멈춘다).
- 장부(SQLite)에 `autoRecovered`와 원래 실패 증거를 함께 남겨 재시작해도 두 번 실행되지 않는다.
  `sw task evidence`와 에이전트 응답에 "자동으로 되돌렸다"가 보인다.

### 2.4 이번에 안 하는 것 (후보로 둠)

- **장애 기억 의미 검색**: 진단 결과와 조치·결과를 SQLite에 남기고 찾기. 첫 단계는 SQLite FTS5
  어휘 검색, 임베딩(로컬 Ollama 등)은 선택. 원본은 언제나 SQLite. 장애 기록이 쌓여야 가치가 생겨서
  뒤로 미룸.
- **모델별 운영 과제 벤치마크**(Claude·Codex·Gemini·Qwen, 같은 과제를 kubectl 직접 vs Shearwater로):
  수치로 장점을 보이는 데 가장 좋지만 실행 비용·시간이 커서 이번 기능이 굳은 뒤 따로 한다. 기존
  세 모델 시험 하네스(`maintenance/20261119-three-models/`)를 확장한다.

## 3. 컨트롤 플레인 고가용성

### 3.1 선택지

| | (A) Raft 복제 저장소, 컨트롤 플레인 3대 이상 | (B) 능동/대기 + 증인 |
| --- | --- | --- |
| 필요한 서버 | 데이터를 가진 컨트롤 플레인 3대 | 데이터를 가진 컨트롤 플레인 2대 + **증인**(데이터 없음, 투표만. 기존 워커나 아무 작은 머신) |
| 견디는 장애 | 3대 중 아무 1대 | 리더·대기·증인 중 아무 1대 |
| 쓰기 지연 | 과반(리더+1대) 확인까지 1왕복 | 대기 서버 확인까지 1왕복 |
| 직접 짤 양 | Raft 핵심(임기·투표·로그 일치·충돌 정리·스냅숏 설치) + 멤버 변경 | 복제 스트림 + 임대 + 작은 증인. 로그가 한 줄로만 흘러 충돌 정리가 단순해 |
| 운영 이해 | "3대 중 2대 살아 있으면 된다" | "주 서버와 대기 서버, 동점일 때 한 표 주는 증인" |
| 데이터 사본 | 3개 | 2개(대기가 죽으면 증인 허락을 받고 잠시 1개) |
| 나중 확장 | 5대 등으로 확장 쉬움 | 2대 고정. 더 필요하면 (A)로 |

**2대만으로는 자동 전환이 안전하지 않아.** 두 서버 사이 연결만 끊긴 경우와 상대가 죽은 경우를 구분할
수 없어서, 자동으로 넘기면 둘 다 리더가 되거나(갈라짐) 확인받은 쓰기를 잃어. 그래서 원래 (B)안의
"임대로 리더를 뽑는다"는 **과반이 내주는 임대**여야 하고, 세 번째 표로 증인을 둔다. 증인 없이 2대만
쓰면 자동 전환은 끄고 `sw ha promote --force`(사람이 판단)만 허용한다.

**추천: (B) 능동/대기 + 증인.** 근거:

- 경량화: 데이터를 가진 서버는 2대면 되고, 세 번째는 이미 있는 워커가 표만 던지면 돼. 대기 서버는
  평소에 워커로 앱을 돌린다(놀지 않음).
- 사용자 편의성: 구성 명령이 `sw node token --control-plane` → `sw join … --control-plane` 하나 더
  늘 뿐이고, 상태는 `sw ha status` 한 화면이야.
- 직접 짜기: 지금 구조(쓰기 주체 하나, 리비전 순서 로그)를 그대로 살려. 복제는 "대기 서버가 리더의
  쓰기 묶음을 순서대로 받아 같은 SQL을 실행"이라 검증하기 쉬워. Raft를 직접 짜는 건 가능하지만
  충돌 정리·멤버 변경에서 버그가 숨기 쉽고, 라이브러리를 쓰면 `go.mod`가 늘어.
- 복제 로그·적용·스냅숏(3.3)은 (A)와 공통이라 나중에 (A)로 가도 버리지 않는다.

**이 결정은 사용자에게 묻는다** (6절).

### 3.2 (B)의 구성

```
        kubectl / sw / 워커                 증인 W (투표만, 데이터 없음)
              │  (주소 2개를 안다)              ▲   ▲
              ▼                                │   │ 하트비트·투표
   ┌──────────────────┐   쓰기 묶음 스트림   ┌──────────────────┐
   │ 컨트롤 플레인 A   │ ───────────────▶ │ 컨트롤 플레인 B   │
   │ 리더: API·컨트롤러 │ ◀─────────────── │ 대기: DB 사본      │
   │ SQLite 원본       │   적용 확인(ack)    │ + 워커로 앱 실행   │
   └──────────────────┘                    └──────────────────┘
```

- **에포크(epoch)**: 리더가 바뀔 때마다 1 오른다. 모든 복제·하트비트·투표 메시지에 싣고, 낮은
  에포크 메시지는 거절한다. A·B·W 모두 디스크(`ha.json`)에 기억한다.
- 대기 서버는 6443에서 받은 연결을 **리더에게 그대로 넘긴다**(TCP 중계). 그래서 어느 주소로 붙어도
  리더가 답한다. 리더가 바뀌면 새 리더가 직접 답한다.

### 3.3 복제 로그

- 모든 쓰기 트랜잭션(객체·`changes`·주소 할당·`meta` 장부·`credentials`·`agent_operations`·새 표)을
  저장소 안에서 **SQL 문장 묶음**으로 기록한다. 표 `replog(seq INTEGER PRIMARY KEY, epoch INTEGER NOT
  NULL, data BLOB NOT NULL, at TEXT NOT NULL)`. `data`는 `[(SQL, 인자…)…]`를 타입을 보존해 인코딩한 것.
- `seq`는 커밋된 쓰기 트랜잭션마다 1 오른다(객체 리비전과 별개: 장부만 바뀌는 쓰기도 seq를 가진다).
- **결정성**: 문장 결과는 인자만으로 정해져야 한다. 시각·UID·난수는 Go에서 만들어 인자로 넘긴다.
  `CURRENT_TIMESTAMP`·`random()`·`datetime('now')`는 저장소 SQL에 쓰지 않는다(시험으로 검사).
- 대기 서버는 같은 문장을 같은 순서로 **한 트랜잭션**에서 실행하고 같은 `replog` 행도 넣는다. 그래서
  두 DB는 같은 상태가 되고, 대기 서버가 리더가 되면 바로 다음 seq부터 이어 쓴다.
- HA를 켜지 않은 설치는 `replog`를 쓰지 않는다(지금과 같음). 오래된 `replog`는 최근 1만 개·1시간을
  넘으면 정리한다. 대기 서버가 정리된 seq보다 뒤처졌거나, 역할이 바뀐 뒤 다시 붙을 때는 **전체
  스냅숏**(SQLite backup API)부터 받는다. DB가 작아서(수 MB) 매번 스냅숏이 가장 단순하고 안전하다.

### 3.4 커밋 순서 (세미싱크)

리더의 `Store.Write`:

1. 쓰기 잠금을 잡고 SQLite 트랜잭션에서 문장을 실행하며 묶음을 모은다. **아직 로컬 커밋 전**.
2. 동기 모드면 묶음을 대기 서버에 보내고, 대기 서버가 **자기 DB에 커밋한 뒤** 보내는 확인(ack)을
   기다린다(기본 2초).
3. 확인이 오면 로컬 커밋 → watch 깨우기 → 클라이언트에 성공.
4. 확인이 안 오면 증인에게 "B를 동기 대상에서 뺀다(에포크 E)"를 요청한다. 증인이 디스크에 기록하고
   승낙하면 **단독 모드**로 바꾸고 로컬 커밋한다. 증인도 답이 없으면 트랜잭션을 되돌리고
   `503 retry=safe`. (이때는 리더도 곧 임대를 잃는다.)

결과:

- 리더에서 읽히는 데이터는 언제나 대기 서버에도 있다(또는 증인이 단독 모드를 인정했다). 그래서
  **클라이언트가 성공 응답을 받은 쓰기는 장애 전환 뒤에도 남는다.**
- 대기가 확인한 뒤 리더가 로컬 커밋 전에 죽으면 그 쓰기는 B에만 있다. B가 리더가 되면 남는다.
  클라이언트는 응답을 못 받았으니 일반 타임아웃과 같은 "적용됐을 수도 있음"이야.
- 단독 모드의 리더는 대기 서버가 다시 붙어 따라잡으면 증인에게 "B 동기 복귀"를 알리고 동기 모드로
  돌아간다.

### 3.5 임대·장애 감지·선출

시간 값은 각 서버의 **단조 시계**로 잰다(벽시계가 튀는 이 PC의 WSL에서도 안전하게). 기본값:
하트비트 1초, 리더 임대 5초, 대기 서버 실패 판정 6초, 증인 투표 대기 7초.

- 리더는 1초마다 B(복제 스트림)와 W에 하트비트를 보낸다. **B나 W 중 하나라도** 확인해 준 하트비트의
  보낸 시각 + 5초까지만 리더다. 그 시간이 지나면 쓰기를 멈추고(503) 물러난다.
- B는 6초 동안 리더에게서 아무것도 못 받으면 W에 에포크 E+1 투표를 청한다. W는 다음을 모두 만족할
  때만 준다: ① E+1이 W가 아는 에포크보다 크다 ② B가 동기 대상이다 ③ W도 7초 넘게 리더 하트비트를
  못 받았다. 그러면 B는 {B, W} 과반으로 리더가 된다. W는 에포크 E+1, 리더 B, 동기 대상 없음을 기록한다.
- 한 번에 한 에포크에 한 표. 같은 에포크에 두 번째 후보는 거절된다.
- 리더가 B와만 끊기고 W와는 닿으면: 리더는 W로 임대를 유지하고 단독 모드로 간다. B는 투표를
  못 받는다(동기 대상이 아니고, 리더 하트비트가 살아 있으니까). 갈라짐 없음.
- 증인만 죽으면: A·B가 동기 모드로 계속. 이어서 리더까지 죽으면 자동 전환은 안 된다(1대만 남음)
  → `sw ha promote --force`.

### 3.6 역할 바꾸기

- **다시 시작한 서버는 언제나 대기로 시작한다.** 살아 있는 리더가 있으면 따라가고(전체 스냅숏부터),
  없으면 선출에 참여한다. 그래서 리더를 재시작하면 대기 서버로 전환이 일어난다(계획된 전환).
- 승격은 `ha.json`의 역할을 바꾼 뒤 **자기 자신을 같은 인자로 다시 실행**(`exec`)한다. 컨테이너는
  containerd가 들고 있어서 그대로 산다. 새 프로세스는 리더 모드로 API·컨트롤러·노드 API를 띄우고,
  자기 노드 에이전트는 DB를 직접 읽는 방식으로 바뀐다. 이때 노드의 Pod 대역은 자기 Node 객체의
  `podCIDR`을 쓴다(지금은 컨트롤 플레인 노드가 `10.244.0.0/24`를 고정으로 씀 → 고친다).
- 물러난 옛 리더는 DB를 지우지 않고 `state.db.diverged-<에포크>`로 옮겨 두고 새 리더의 스냅숏을 받는다.
- 두 컨트롤 플레인 모두 워커용 노드 자격 증명을 갖는다(대기일 때는 워커로 앱을 돌리므로).

### 3.7 클라이언트가 주소 여러 개를 아는 법

- **워커**: `node.json`에 컨트롤 플레인 주소 목록. 노드 API 클라이언트는 연결 실패나
  `503 standby`면 다음 주소로 넘어간다. join 응답에 목록이 들어 있고, 바뀌면 하트비트 응답으로 갱신한다.
- **kubectl**: kubeconfig 형식은 클러스터마다 `server`를 하나만 가진다. 그래서
  - 서버 인증서에 두 컨트롤 플레인 주소와 선택 이름(`--ha-name`, 예: `sw-api.internal`)을 모두 넣고,
  - `sw kubeconfig`는 그 이름(없으면 첫 주소)을 쓰고, 컨트롤 플레인마다 직접 붙는 컨텍스트도 함께 쓴다.
  - 그 이름을 DNS나 `/etc/hosts`에서 두 주소로 풀어 두면 kubectl(Go)은 첫 주소가 안 되면 다음 주소로
    붙는다. 대기 서버가 리더로 중계하므로 둘 중 아무 쪽이 살아 있어도 된다.
- **`sw` CLI·MCP**: 연결 정보에 주소 목록을 두고 차례로 시도한다.

### 3.8 구성 명령

```
# 컨트롤 플레인 A (지금처럼)
sw up --advertise-address 10.0.0.10
sw node token --control-plane          # B에서 실행할 한 줄을 출력
sw node token --witness                # 증인에서 실행할 한 줄을 출력

# 컨트롤 플레인 B
sw join https://10.0.0.10:6443 --token swj_... --ca-hash sha256:... --control-plane
sw up                                  # 대기로 시작

# 증인 W (워커여도 되고, root·containerd 없는 머신이어도 됨)
sw join https://10.0.0.10:6443 --token swj_... --ca-hash sha256:... --witness
sw ha witness                          # 또는 서비스로

sw ha status                           # 리더·에포크·동기 상태·마지막 seq·증인
sw ha promote --force                  # 증인 없이 사람이 승격(위험을 출력하고 확인을 받음)
```

### 3.8.1 구현하며 정한 것 (2026-11-25)

- **복제는 리더의 6443 위 긴 폴링**(`/shearwater/ha/v1/stream?after=N`): 대기 서버가 다음 요청에 실은
  `after`가 곧 확인(ack)이야. 컨트롤 플레인에는 새 포트가 필요 없고, 증인만 6445를 연다.
- 리더는 확인을 기다리는 묶음(아직 로컬 커밋 전)을 메모리로만 대기 서버에 건넨다. 그래서 대기 서버가
  받은 적 없는 쓰기가 리더에서 읽히는 일은 없다.
- **임대는 대기 서버가 동기일 때만** 지킨다. 대기를 증인 허락으로 뺀 단독 리더는 증인이 그 대기를 뽑지
  않으니 임대 없이 계속 쓴다(대기·증인이 차례로 죽어도 리더가 멈추지 않게).
- 동기에서 빠진 대기 서버가 다시 폴링하면, 다음 쓰기가 최대 `SyncTimeout` 동안 그 대기 서버가 지금까지
  커밋된 묶음을 모두 확인하기를 기다린 뒤 증인에게 동기 복귀를 알린다(쓰기가 몰려도 영원히 못 따라잡는
  일이 없게).
- **대기 서버는 리더가 어디 있는지 확실할 때만 중계**한다(스냅숏을 받았고 `FailAfter` 안에 소식을 들음).
  두 서버가 서로를 리더로 알고 연결을 주고받는 고리를 막는다.
- 역할 전환은 `/proc/self/exe`로 **같은 PID에서 다시 실행**한다. `sw up`이 기록한 인스턴스와 잠금,
  컨테이너가 그대로 이어진다. 선거에서 이긴 프로세스만 `ha.json`의 nonce와 환경 변수로 리더로 시작한다.
- 리더는 고가용성을 켤 때 자기 노드의 워커 자격 증명(`<config>/standby/`)을 만들어 둔다. 물러나면 그걸로
  새 리더의 워커가 된다. 노드 토큰은 credentials 표에 있어 복제된다.
- `Store.Fence`와 `ReplicationState`는 쓰기 잠금을 잡지 않는다. Replicator가 쓰기 잠금을 쥔 채
  기다리는 동안 부르기 때문이다(시험에서 교착을 찾아 고침).

### 3.9 보장하는 것 / 안 하는 것

- 보장: 리더·대기·증인 중 **한 대**가 죽거나 끊겨도, 성공 응답을 받은 쓰기는 사라지지 않는다. 증인과
  남은 컨트롤 플레인이 살아 있으면 사람 없이 전환된다. 워커의 앱은 전환 중에도 계속 돈다.
- 안 함: 두 대 동시 장애, 네트워크가 갈렸을 때 소수 쪽의 쓰기(거절), 대기 서버에서의 읽기 분산,
  컨트롤 플레인 3대 이상, 자동 멤버 교체. 전환에 걸리는 시간은 QA에서 재서 적는다.
- 서버 간 복제 연결은 HTTPS(클러스터 CA) + 컨트롤 플레인 전용 자격 증명. 증인 연결도 같다.

## 5. QA

- 단위: 각 기능별(2.3.x) + 복제(문장 기록·적용·스냅숏·결정성 검사), 선출(증인 투표 규칙, 에포크 거절,
  임대 만료 뒤 물러남), 세미싱크(확인 전 로컬 미커밋, 확인 없음 → 증인 → 단독/503).
- 실제: QA 배포판 `Shearwater-Alpha-QA-20261112`에서 여러 서버 하네스(`maintenance/20261124-multinode-
  tenancy/qa/mn.py`)를 복사해 A·B·W(+워커)로 띄우고,
  1. 쓰기를 계속 넣는 중에 **리더 프로세스를 죽인다** → 성공 응답을 받은 쓰기가 모두 새 리더에 있는지
     (리비전·UID 대조), kubectl(이름 하나에 주소 둘)과 워커가 다시 붙는지, 앱 요청 오류.
  2. 옛 리더를 다시 켠다 → 대기로 돌아와 따라잡는지.
  3. 대기 서버를 죽인다 → 증인 허락으로 단독 모드, 쓰기 계속.
  4. 증인을 죽인다 → 동기 모드 계속.
- 에이전트 기능: `sw agent add` → 그 연결로 `sw mcp` 도구 호출, 다른 네임스페이스 거절, `sw changes`에
  행위자가 보이는지, 두 작업이 같은 앱을 잡을 때 `APP_LEASED`, 일부러 깨진 이미지로 자동 되돌리기.
