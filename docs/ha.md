# 컨트롤 플레인 두 대: 대기 서버와 증인

[English](en/ha.md) · **한국어**

alpha.16까지 컨트롤 플레인은 한 대였어. 워커는 여러 대 붙일 수 있었지만 컨트롤 플레인 서버가 죽으면
API와 재배치가 멈췄어(워커의 앱은 계속 돌아). 이 문서는 **컨트롤 플레인을 두 대로** 두는 방법이야.
설계와 근거는 [설계 문서 3절](design-agent-first-ha.md#3-컨트롤-플레인-고가용성)에 있어.

## 어떻게 동작하나

```
        kubectl · sw · 워커 (주소 두 개를 안다)
              │
   ┌──────────▼─────────┐  쓰기 묶음   ┌────────────────────┐
   │ 컨트롤 플레인 A     │ ──────────▶ │ 컨트롤 플레인 B     │
   │ 리더: API·컨트롤러   │ ◀────────── │ 대기: DB 사본       │
   │                    │   확인       │ + 워커로 앱 실행     │
   └──────────┬─────────┘             └─────────┬──────────┘
              │      하트비트·투표                 │
              └────────────▶ 증인 W ◀────────────┘
                       (데이터 없음, 한 표)
```

- **리더**가 API를 받아. 대기 서버가 **동기 상태**(모든 묶음을 따라잡고 증인이 인정함)면, 모든 쓰기
  트랜잭션을 대기 서버가 자기 DB에 커밋했다고 확인한 뒤에야 자기 DB에 커밋하고 성공을 돌려줘. 그래서
  성공 응답을 받은 쓰기는 리더가 갑자기 죽어도 대기 서버에 있어. 대기 서버가 막 합류했거나 빠졌다가
  돌아오는 동안에는 리더가 증인의 허락을 받고 혼자 쓰고, 대기 서버가 따라잡는 즉시(쓰기가 없어도)
  동기로 돌아와. 동기가 아닌 대기 서버는 증인이 뽑지 않으니 오래된 사본이 리더가 될 일은 없어.
- **대기 서버**는 평소에 리더의 워커로 앱을 돌리고, 6443으로 오는 연결을 리더에게 그대로 넘겨. 그래서
  kubectl이나 워커가 둘 중 어느 주소로 붙어도 돼.
- **증인**은 데이터 없이 표만 던져. 리더가 끊겼을 때 대기 서버가 넘겨받아도 되는지(리더가 정말 멈췄는지,
  대기 서버가 최신인지)를 판정해. 두 대만으로는 "상대가 죽었다"와 "연결만 끊겼다"를 구분할 수 없어서
  세 번째 표가 필요해. 증인은 워커나 아무 작은 리눅스 머신에서 돌리면 되고, root나 containerd가
  필요 없어.

## 구성

필요한 것: 서로 닿는 리눅스 서버 세 대(컨트롤 플레인 두 대 + 증인). 증인은 기존 워커여도 돼.
열어야 하는 포트: 컨트롤 플레인 6443(TCP), 증인 6445(TCP), 노드 사이 VXLAN 8472(UDP)와 다른 노드
Pod의 `kubectl logs` 중계용 10250(TCP).

```bash
# 1. 컨트롤 플레인 A (지금처럼)
sudo sw up --advertise-address 10.0.0.10

# 2. A에서: 두 번째 컨트롤 플레인과 증인용 한 줄씩
sudo sw node token --control-plane
sudo sw node token --witness

# 3. 컨트롤 플레인 B: 2에서 나온 control-plane 줄을 실행한 뒤
sudo sw join https://10.0.0.10:6443 --token swj_... --ca-hash sha256:... --control-plane
sudo sw up                                   # 대기로 시작해

# 4. 증인 W: 2에서 나온 witness 줄을 실행한 뒤 증인을 띄워(서비스로 두는 걸 권해)
sw join https://10.0.0.10:6443 --token swj_... --ca-hash sha256:... --witness --config-dir ~/.config/shearwater-witness
sw ha witness --config-dir ~/.config/shearwater-witness

# 상태
sudo sw ha status
```

`sw node token --control-plane`을 처음 실행할 때 A가 고가용성을 켜(`ha.json`을 만들고 쓰기 묶음을 기록하기
시작해). 그 전까지는 지금과 똑같이 한 대로 돌아.

## 클라이언트가 주소 두 개를 아는 법

- **워커**는 합류할 때 컨트롤 플레인 주소 목록을 받아 `node.json`에 기억하고, 한쪽이 안 되면 다른 쪽으로
  넘어가. 목록이 바뀌면 응답 헤더로 배워.
- **kubectl**: kubeconfig에는 서버 주소가 하나뿐이야. 대기 서버가 연결을 리더로 넘기므로 **대기 서버의
  주소**를 써도 평소에 동작하고, 그 서버가 리더가 되면 그대로 이어져(QA에서 확인). 서버 인증서에는 두
  컨트롤 플레인의 IP가 모두 들어 있어서 어느 IP로 붙어도 검증돼. 그 대기 서버 자체가 죽으면 다른
  컨트롤 플레인의 IP로 바꿔 붙어(두 주소에 각각 컨텍스트를 두면 편해). 이름(DNS)은 아직 인증서에 넣지
  않으니 kubeconfig에는 IP를 써.

## 장애가 나면

| 상황 | 결과 |
| --- | --- |
| 리더가 죽음 | 6초 동안 소식이 없으면 대기 서버가 증인에게 표를 청하고, 증인은 리더 하트비트가 7초 넘게 끊긴 걸 확인한 뒤 줘. 대기 서버가 같은 PID로 다시 시작해 리더가 돼. QA에서 걸린 시간은 아래 표 |
| 대기 서버가 죽음 | 다음 쓰기가 2초 기다린 뒤, 증인의 허락을 받아 리더 혼자 계속 써(그동안 사본은 하나) |
| 증인이 죽음 | 두 컨트롤 플레인이 그대로 계속. 이어서 리더까지 죽으면 자동 전환은 안 돼 |
| 리더가 대기 서버·증인 둘 다와 끊김 | 대기 서버가 동기 상태였다면 리더가 임대(5초)를 잃고 쓰기를 멈춘 뒤 대기로 다시 시작해(갈라짐 방지). 대기 서버를 이미 증인 허락으로 뺀 단독 리더는 그대로 계속 써(그 대기 서버는 뽑히지 않으니까) |
| 옛 리더가 돌아옴 | 언제나 대기로 시작해 새 리더의 스냅숏을 받아. 원래 DB 파일은 지우지 않고 `state.db.replaced-<시각>`으로 옆에 둬 |

다시 시작한 컨트롤 플레인은 원칙적으로 대기로 시작해. 예외: 컨트롤 플레인이 혼자이거나, 증인 없이 두
대인데 방금까지 리더였고 상대가 더 새 에포크의 리더가 아니면 바로 리더로 시작해. 증인이 있으면 방금까지
리더였던 서버는 증인에게 곧바로 다음 에포크를 받아 다시 리더가 돼(재시작 때마다 전환이 일어나지 않게).

**증인 없이 두 대만** 쓰면 자동 전환은 꺼져 있어. 리더가 정말 사라졌다고 판단될 때만 대기 서버에서
`sudo sw ha promote --force`를 실행해. 옛 리더가 살아 있는 채로 이걸 하면 두 서버가 각자 쓰게 되니,
옛 리더를 확실히 끈 뒤에만 해.

## 보장하는 것과 안 하는 것

- 보장: 리더·대기·증인 중 **한 대**가 죽거나 끊겨도, 성공 응답을 받은 쓰기는 사라지지 않아. 증인과 남은
  컨트롤 플레인이 살아 있으면 사람 없이 넘어가. 워커의 앱은 전환 중에도 계속 돌아.
- 안 함: 두 대 동시 장애, 네트워크가 갈렸을 때 소수 쪽의 쓰기(거절돼), 대기 서버에서 읽기 나누기,
  컨트롤 플레인 세 대 이상, 자동 멤버 교체.
- 응답을 못 받은 쓰기(전환 순간 503 `NOT_LEADER`나 연결 끊김)는 적용됐을 수도, 안 됐을 수도 있어.
  다시 시도하기 전에 확인해.
- 서버 사이 복제와 증인 연결은 HTTPS(클러스터 CA)와 클러스터 HA 토큰(`ha.json`, root만 읽음)으로 보호해.
