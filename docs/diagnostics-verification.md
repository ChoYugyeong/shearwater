# 진단 CLI 검증 기록 — 2026-11-13

대상은 공개 alpha.2 소스에서 이어서 구현한 **미발행 `0.1.0-alpha.3-dev`**야.
`sw get`, `logs`, `events`, `why`와 [문제 해결 안내](troubleshooting.md)를 추가했어.
이 기록은 실제 수행한 검사와 범위를 설명하며 새 릴리스 발행 기록은 아니야.

## 확인한 내용

| 검사 | 실제 결과 |
|---|---|
| `bash hack/t.sh ./...` | gofmt 확인·go vet·전체 Go 테스트 통과. 가짜 런타임을 쓰는 기존 노드 검사 포함 |
| Python 기존 검사 | `python3 -m unittest discover -s hack -p 'test_*.py'`: 40개 통과 |
| API M1 | Linux kubectl 1.36.6 + Windows kubectl 1.36.0: **103 통과, 0 실패** |
| API M0 | 같은 두 클라이언트: **47 통과, 0 실패** |
| 실제 진단 장애 검사 | `hack/diagnostics-check.sh`: **16 통과**, 검사용 sw 정지·컨테이너 정리 성공 |
| 의존성·빌드 | `go mod verify`, Linux amd64/cgo 없는 빌드, 버전 일치 검사 통과 |
| 고지 파일 | 실행 파일의 외부 모듈 46개와 고지 목록 일치 |
| Kubernetes 의존 경계 | `go list -deps ./cmd/sw`, `go version -m dist/sw`에서 `k8s.io/*` import/링크 0개 |
| 기존 서버 호환 | 실행 중인 alpha.2 API에 새 CLI의 네 읽기 명령을 사용해 모두 성공 |
| 변경분 비밀정보 검사 | gitleaks의 redacted 출력으로 커밋할 패치를 검사, 발견 0 |

최종 Linux 실행 파일 SHA-256은
`008efd363fe8f3577ff6e2101a3bc1fa6386e7864f634b1ea4d8f33230987b98`이야.
설명 주석을 마무리한 뒤 다시 빌드한 이 파일로 실제 장애 16개를 다시 통과했고,
기존 alpha.2 서버에서 여덟 종류의 `get`과 logs/events/why/version 총 12개 호출을 확인했어.
SHA-256은 검사한 파일을 구분하는 지문이며 공개 릴리스 자산의 체크섬은 아니야.

Go 검사는 인증된 실제 HTTPS 요청, 인자 위치·범위 검사, 전체 JSON의 큰 정수 보존,
HTTP 오류/타임아웃, 조회 도중 Pod 재생성·컨테이너 재시작에 따른 `CONFLICT`,
stdout 부분 출력 방지, 제어 문자 처리, 빠진 로그 근거 표시를 다뤄.
실제 SQLite API를 조회한 뒤 저장 리비전과 클라이언트 설정 파일이 바뀌지 않는 것도 확인했어.

## 실제 장애는 어떻게 만들었나?

기존 앱이 없는 별도 WSL Ubuntu 24.04에서 containerd 2.2.1을 전용 소켓·데이터 경로로
시작했어. 원래 앱이 쓰는 네트워크와 겹치지 않도록 전용 네트워크 네임스페이스를
사용했어. Go 1.27.3, Linux kubectl 1.36.6을 사용했고 이 작업에서 패키지를 설치하지 않았어.
Docker/containerd 설정 파일과 다른 containerd 네임스페이스는 읽거나 바꾸지 않았어.

| 상황 | 실제 입력·관찰 | 확인한 진단 |
|---|---|---|
| 이미지 다운로드 실패 | 격리 netns에서 열려 있지 않은 loopback 레지스트리 주소 | 이미지 오류와 다음 확인, 시작 전 로그 부재, 해당 UID의 이벤트 |
| 반복 종료 | BusyBox가 표시 문자열을 쓴 뒤 exit 7, `restartPolicy: Always` | CrashLoopBackOff, 직전 종료 7, 현재/직전 로그와 명시적 `--previous` |
| 잘못된 볼륨 종류 | 실제 파일을 `hostPath.type: Directory`로 지정 | `CreatePodSandboxError`의 실제 메시지와 볼륨 확인 안내 |
| 없는 실행 파일 | 이미지에 없는 경로를 `command`에 지정 | `RunContainerError`, 실행 파일 확인 안내, 없는 로그를 정상으로 꾸미지 않음 |
| 재시작하지 않는 실패 | 문자열을 쓴 뒤 exit 9, `restartPolicy: Never` | Failed 상태, 현재 종료 9와 해당 실행 로그 |
| 컨테이너 두 개 | 서로 다른 문자열을 쓰는 left/right | `-c` 생략 거절, 선택한 로그만 출력, tail 0·바이트 제한, Ready 해석의 한계 |
| 목록·이벤트·오류 | 라벨로 목록 읽기, UID로 이벤트 읽기, 없는 Pod 조회 | 전체 JSON 6개 Pod, 리비전·UID 필터, NOT_FOUND와 빈 stdout |
| 같은 이름 재생성 | 이미지 실패 Pod를 지우고 같은 이름으로 다시 생성 | 새 UID의 이벤트만 선택 |

처음 검사에서는 볼륨 오류를 `CreateContainerConfigError`라고 예상해서 기다리다 실패했어.
실제 상태는 `CreatePodSandboxError`였어. 이는 볼륨 준비가 컨테이너 생성보다 앞서기 때문이야.
테스트 기대값을 실제 경로에 맞추고, CLI에도 볼륨과 네트워크를 구분해서 확인하도록 안내를
추가했어. 없는 실행 파일의 `RunContainerError` 안내도 보완한 뒤 전체 장애 검사를 다시 통과했어.
노드·런타임의 오류 이유를 진단 문구에 맞춰 바꾼 것은 아니야.

검사 후 전용 containerd·netns·uplink 규칙을 정리했고 증거·DB·로그는 보존했어.
각 실행은 ext4의 별도 `diagnostics.*` 디렉터리를 사용했어. 실패한 첫 실행의 자료도 남겨뒀어.

## 기존 앱 보존 확인

장애 실험 전 점검에서 원래 WSL 서버의 `/run` 실행 기록과 앱 프로세스가 사라져 있었고,
Windows 접속 주소도 연결을 거절했어. 이때는 QA 장애를 만들기 전이었어.
중단을 일으킨 명령이나 원인은 이번 검사로 확인하지 못했어.

원래 설치된 alpha.2 파일·DB·인증·앱 파일을 확인한 뒤 **같은 실행 파일과 옵션**으로
`sw up`해서 기존 앱을 복구했어. Windows 접속용 기존 중계도 같은 주소로 다시 시작했어.
새 진단 버전으로 서버를 교체하거나 앱을 재배포하지 않았어.

복구 시 Pod UID·Pod IP·Service IP·앱 선언·설정·파일 해시는 유지됐어.
컨테이너가 다시 실행돼 재시작 횟수는 **2 → 3**이 됐고, 연결 대상 목록인 EndpointSlice는
준비 상태가 바뀌는 동안 컨트롤러가 재생성했어. 이 변경을 “전부 동일”이라고 처리하지 않았어.

복구 완료 뒤부터 격리 장애 실험 전후를 다시 비교했어.

| 비교 항목 | 결과 |
|---|---|
| 실제 sw 서버 | alpha.2, 같은 PID·시작 기록 유지 |
| 앱 Pod·태스크 | 같은 UID·컨테이너 ID·태스크 PID, 재시작 수 **3 → 3** |
| Pod IP·Service IP | 같은 주소 유지 |
| 설정 파일 | 8개 내용 해시·권한·소유권 동일 |
| 앱 배포 파일 | 32개 내용 해시·권한·소유권 동일 |
| SQLite | `integrity_check=ok`, 객체 10개 선언·소유 관계·IP 예약 2개 동일 |
| Pod/Service HTTP | 전후 200, HTML 5,303바이트와 내용 해시 동일 |
| Windows 접속 관측 | 약 418.945초 동안 **209/209 HTTP 200**, 본문 해시 불일치 0 |

이 관측은 표본 사이의 모든 순간까지 무중단을 보증하지 않아. 앞서 발견한 서버 중단·복구와
복구 뒤의 보존 검사를 구분해야 해. 브라우저 저장소를 새로 검사한 것은 아니며,
브라우저 프로필·localStorage·앱 URL을 변경하지 않았어.

## 이번에 하지 않은 것

- GitHub push, 새 태그/릴리스 발행, 운영 서버의 새 진단 버전 교체.
- 새 장시간 부하·의도적인 WSL 재부팅 실험. 기존 기록을 이번 검사로 합산하지 않아.
- 다른 CPU 아키텍처·다중 노드·프로브 실행·private registry 인증 검증.
- 새 동료 리뷰 승인. 이 문서의 결과는 구현자가 직접 실행해 확인한 기록이야.

증거에는 인증 파일 경로와 앱 로그가 포함될 수 있어 공개 저장소에 넣지 않았어.
재현 가능한 검사 코드와 위 결과 요약을 남겼고, 전체 로컬 로그·상태 사본은 작업별
비공개 검증 폴더 및 해당 WSL의 Shearwater 검사 디렉터리에 보관했어.
