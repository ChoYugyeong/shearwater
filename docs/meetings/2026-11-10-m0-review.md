M0 kubectl 호환 리뷰: 정상인 토대는 확인했고, M1 공통 쓰기 경로에 옮기기 전에 고칠 항목은 generation·finalizer·Strict 디코딩이다. 아래는 dd3e581을 git show로 읽은 정적 검토이며 테스트 재실행 결과는 아니다. 검토 중 HEAD는 ae8666b로 이동했지만 dd3e581 이후 커밋 diff는 문서 3개뿐이었다. 작업 파일은 수정하지 않았다.

1. handlers / store (설계 3.2·3.4·5)

- [확정, P2] handlers.go:311의 “모든 종류에서 spec만 비교”는 Deployment에 부족하다. upstream은 spec OR metadata.annotations 변경 시 generation++이다(주석을 RS로 복사하기 때문). 재현 자료: Deployment 생성 → spec 그대로 annotation만 PUT → generation은 +1, label만 PUT 또는 status PUT은 그대로. apply의 last-applied annotation도 이 규칙에 포함된다. 설계 3.4의 “spec만”도 같이 보완 필요. Service는 upstream 전략이 spec 변경 때 generation을 올리지 않으므로 종류별 정책으로 두는 편이 정확하다.
  근거: https://github.com/kubernetes/kubernetes/blob/v1.36.6/pkg/registry/apps/deployment/strategy.go#L110 ; pkg/registry/core/service/strategy.go의 PrepareForUpdate.

- [확정, P2] 삭제 중 새 finalizer 추가를 막는 metadata update 검증이 없다. finalizer=[a] 생성 → DELETE → GET 객체에 b 추가해 PUT하면 현재 경로는 받아들인다. upstream 기대값은 422/Invalid, metadata.finalizers 원인이다. 이미 있던 finalizer 제거는 허용한다. Namespace처럼 현재 갱신 경로가 없는 리소스에는 사용자 finalizer를 받을지 별도 제한도 필요하다.
  근거: https://github.com/kubernetes/kubernetes/blob/v1.36.6/staging/src/k8s.io/apimachinery/pkg/api/validation/objectmeta.go#L312

- [확정, P2] Strict 디코딩은 unknown만으로 충분하지 않다. internal/apis/decode.go가 먼저 map으로 읽으므로 중복 JSON 키를 잃는다. 예: spec.replicas를 1, 2 두 번 보낸 Strict 요청은 upstream 400이어야 한다. Warn은 경고 후 마지막 값, Ignore는 마지막 값이다. 또한 handlers.go:120의 fieldValidation enum 검사가 unknown이 있을 때만 실행돼 정상 필드만 든 fieldValidation=Maybe 요청은 통과한다. /status는 별도 Unmarshal 경로라 이 검사를 통째로 우회한다. M1 PATCH도 “패치 지시어 적용 → 최종 객체 검증”과 “원문 중복 키 검출”을 구분해 공유할 것.
  근거: https://github.com/kubernetes/kubernetes/blob/v1.36.6/staging/src/k8s.io/apimachinery/pkg/runtime/serializer/json/json.go#L267

- [정상] 일반 PUT의 status 보존, /status의 generation 불변, 전달된 낡은 RV의 409, UID precondition, 즉시 DELETE의 Status.details.uid와 대기 DELETE의 객체 반환은 방향이 맞다. 빈 RV를 허용하는 PUT 자체는 버그가 아니다: Pod/Deployment/Service upstream 전략도 AllowUnconditionalUpdate=true다. finalizer가 남았다고 무조건 HTTP 202로 바꿀 필요도 없다(현재 upstream도 일반 pending delete는 200).
  근거: pkg/registry/{core/pod,core/service,apps/deployment}/strategy.go의 AllowUnconditionalUpdate; https://github.com/kubernetes/kubernetes/blob/v1.36.6/staging/src/k8s.io/apiserver/pkg/endpoints/handlers/delete.go#L179

- [정상 + M1 경계] store.go:216이 같은 read transaction에서 global rev와 목록을 읽으므로 빈 목록/필터 결과에도 snapshot RV를 돌리는 것은 맞다. changes.prev_data와 no-op revision 억제도 watch 토대에 적합하다. 다만 list의 resourceVersion/resourceVersionMatch는 현재 무시되므로 M1에서는 “Exact인데 최신을 200으로 반환”하지 않게 구현 또는 명시 거절을 고정할 것.

- [M2/M3 선행 fixture, 현 단계 미구현과 구분] DeleteOptions gracePeriodSeconds/propagationPolicy를 파싱하지만 실행은 즉시 삭제 또는 finalizer만 보는 상태다. 런타임/GC 추가 때 grace>0인 Pod를 바로 지우거나 Foreground/Orphan을 Background처럼 처리하면 안 된다. 마지막 finalizer 제거의 즉시 삭제 조건도 지금은 grace를 보지 않는다(handlers.go:315). upstream ShouldDeleteDuringUpdate는 기존 grace가 0 또는 nil인 것도 확인한다. 현재 M0의 미스케줄 Pod 즉시 삭제만으로 grace 동작을 판정하지 말 것: upstream도 미스케줄/완료 Pod는 0으로 조정한다.

2. discovery / 최소 OpenAPI (설계 3.1·3.5)

- [확정] PATCH operation의 GVK extension + fieldValidation query parameter면 v1.36의 지원 여부 탐지에는 맞다. query_param_verifier_v3.go의 supportsQueryParamV3가 그대로 검사한다.
  https://github.com/kubernetes/kubernetes/blob/v1.36.6/staging/src/k8s.io/cli-runtime/pkg/resource/query_param_verifier_v3.go#L108
- [소스상 가능, 실제 apply 재검증 필요] 현재처럼 requestBody가 없으면 apply/patcher.go는 v3 SMP schema 경로를 선택하지 않고, 뒤의 built-in 타입 fallback을 쓸 수 있다. 부분적인 SMP requestBody/schema를 추가해 fallback을 끊지 말 것. M1 gate는 --openapi-patch=false 없이 기본 apply 생성→수정→재적용, 두 kubectl 버전과 빈 discovery cache로 고정하는 것이 좋다. 현재 문서는 explain용 완전한 스키마는 아니다.
  https://github.com/kubernetes/kubernetes/blob/v1.36.6/staging/src/k8s.io/kubectl/pkg/cmd/apply/patcher.go#L246
- [M1+] watch/patch verbs는 구현한 뒤 광고. scale은 부모 apps/v1과 응답 타입이 달라 discovery의 deployments/scale에 group=autoscaling, version=v1, kind=Scale이 필요하다. 현재 apiResource 구조에는 group/version 필드가 없다. scale 기본 PATCH 및 조건부 --current-replicas/--resource-version의 GET→PUT도 별도 fixture로 둘 것.

3. Status.message 접두사 (설계 8.3)

- [확인한 명령 경로에서는 문제 없음] apply conflict retry, edit invalid 처리, delete NotFound 판정은 reason/code 및 details.causes를 사용한다. “NOT_FOUND retry=never:” 문자열을 표준 reason 자리에 넣지만 않으면 현재 message 접두사는 유지 가능하다.
  https://github.com/kubernetes/kubernetes/blob/v1.36.6/staging/src/k8s.io/apimachinery/pkg/api/errors/errors.go#L529
  https://github.com/kubernetes/kubernetes/blob/v1.36.6/staging/src/k8s.io/kubectl/pkg/cmd/util/editor/editoptions.go#L839
- retry=never라는 문구가 kubectl 재시도를 제어하지는 않는다. 지연은 HTTP Retry-After 또는 Status.details.retryAfterSeconds 등으로 표현해야 한다. 그리고 422의 kind/name/causes가 있으면 kubectl은 causes 중심으로 출력하여 message의 접두사·힌트를 생략할 수 있다(helpers.go의 checkErr). 사람이 반드시 읽어야 할 수정 힌트는 해당 cause.message에도 두는 편이 좋다.

4. M1 먼저 고정할 자료 (설계 3.6·5·10)

- SMP: (a) containers/env 추가+삭제+순서 변경과 서버 원소 보존 (b) null/누락/[] 차이 (c) $patch delete/replace (d) $setElementOrder와 실제 patch 원소 순서 불일치 거절 (e) finalizers의 $deleteFromPrimitiveList (f) RollingUpdate→Recreate 및 volumes의 $retainKeys (g) 병합 키 누락/중복과 scalar-list 중복 제거 (h) metadata.resourceVersion 충돌 시 전체 rollback.
  바로 옮길 기대값: apimachinery/pkg/util/strategicpatch/patch_test.go의 customStrategicMergePatchTestCaseData 및 createStrategicMergePatchTestCaseData. 서버 테스트에는 current+threeWay→result(또는 original+twoWay→modified/명시된 twoWayResult)를 가져오면 된다. 두-way/세-way “패치 생성”까지 서버가 구현할 필요는 없다. 실제 Pod/Deployment의 merge-key 표 테스트는 이 generic fixture와 따로 둔다.
  https://github.com/kubernetes/kubernetes/blob/v1.36.6/staging/src/k8s.io/apimachinery/pkg/util/strategicpatch/patch_test.go#L327

- Protobuf: 두 kubectl 버전별 Deployment/Service/Namespace 실제 캡처 + Pod(kubectl run) 캡처를 JSON 동등 요청과 비교. UID/시간/RV를 정규화하되 0 replicas, false, 빈 문자열, 빈 message의 존재 여부는 지우지 말 것. magic+runtime.Unknown+Raw 타입 일치, IntOrString 숫자/문자, Quantity, metadata map, 반복 메시지, 잘린 length/varint overflow를 먼저 고정한다. 알려진 필드의 명시적 0과 미래의 모르는 field-number=0값을 같은 규칙으로 버리면 안 된다.
  upstream의 실제 pb/json 짝도 존재 확인: staging/src/k8s.io/api/testdata/HEAD/{apps.v1.Deployment,core.v1.Service,core.v1.Namespace,core.v1.Pod}.{pb,json} (v1.36.6 태그로 고정). 이것들은 지원 밖 필드가 많은 전체 API fixture이므로 Shearwater HTTP create 성공 기대값으로 통째로 쓰지 말고, wire/type 해독 참고 및 지원 범위 투영/명시 거절 검사에 쓸 것.
  https://github.com/kubernetes/kubernetes/tree/v1.36.6/staging/src/k8s.io/api/testdata/HEAD

- watch: false→false 무전송, false→true ADDED, true→true MODIFIED, true→false DELETED(이전 객체 내용 + 새 사건 RV), 실제 삭제, 같은 이름 다른 UID 재생성. labelSelector와 fieldSelector 양쪽에 적용. 바로 가져올 기대값은 cache_watcher_test.go의 TestCacheWatcherHandlesFiltering: enter/leave/re-enter = ADDED@1, DELETED@2, ADDED@3; 다른 시나리오 = ADDED@3, MODIFIED@4, DELETED@5.
  https://github.com/kubernetes/kubernetes/blob/v1.36.6/staging/src/k8s.io/apiserver/pkg/storage/cacher/cache_watcher_test.go#L80
  이어서 snapshot R 직후 쓰기와 구독 시작의 경쟁, 재생 중 compaction 410, 느린 구독자 단절(조용히 drop 금지), sendInitialEvents의 ADDED→초기 끝 BOOKMARK→실시간 순서, dryRun/no-op 이벤트 0개를 고정할 것.

우선순위는 SMP 최종 객체 의미 → watch 경계/전이 → Protobuf 의미 보존. 위 확정 차이를 공통 update/decode 경로에서 먼저 고치면 M1 패치 구현에 같은 결함이 퍼지는 것을 막을 수 있다.
